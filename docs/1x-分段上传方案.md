## 一、现状

### 1.1 旧版 saiadmin 6.x 怎么做的（逐行读源码）

后端 `plugin/saiadmin/service/storage/ChunkUploadService.php`（上游 `5981781` 与 composer 缓存 6.0.11 逐字相同）+ `SystemAttachmentLogic::chunkUpload` + 路由 `POST /core/system/chunkUpload`（权限码 `core:system:chunkUpload`）；前端组件 `sandadmin-artd/src/components/sand/sa-chunk-upload/index.vue`（本仓 main 仍在，`api/auth.ts:168`）。

流程：前端用 SparkMD5 按 2MB 读块算整文件 **MD5** → 按 5MB 切片、**顺序**逐片 `multipart` 提交（字段 `file/ext/size/type/hash/index/total/name`）→ 服务端：

1. `index == 0` 时按 `hash` 查 `sa_system_attachment`，**有就直接返回该附件**（秒传）；否则从 0 开始找第一个不存在的 `{hash}_{total}_{i}.chunk`，回 `resume` 和断点序号。
2. 每片 `move()` 到 `{local_root}chunk/{hash}_{total}_{index}.chunk`。
3. 收到 `index + 1 == total` 那一片就合并：逐片 `file_get_contents` 追加写入 `{local_root}chunk/{hash}.{ext}`，删分片，写附件表（`storage_mode` 固定 1 本地，`mime_type` 取客户端传值）。

默认值：分片 5MB、单文件 1024MB（组件 props `chunkSize: 5`、`maxSize: 1024`）；类型白名单 `upload_allow_file`；`local_root` 默认 `public/storage/`。

读源码发现的问题（1.x 必须不重犯）：

| # | 问题 | 位置 | 后果 |
| --- | --- | --- | --- |
| S1 | `hash`、`total`、`index` 全是客户端原样拼进路径，未校验格式 | `checkChunk`/`uploadChunk`/`mergeChunk` 拼 `$this->path . "{$data['hash']}_..."` | **路径穿越**：`hash` 带 `../` 可往存储根外写文件 |
| S2 | 合并文件落 `public/storage/chunk/`，即 web 根内 | `local_root` 默认值 + `mergeChunk` | 上传物可被直接访问；白名单若被改宽有执行风险 |
| S3 | 秒传只比 `hash`，不看上传人和可见性 | `SystemAttachmentLogic::chunkUpload` | 只要知道别人文件的 MD5 就能拿到其附件记录和 URL |
| S4 | 分片名只由 `hash` 决定，不绑上传人/任务 | 同 S1 | 两人同哈希并发会互相覆盖分片；可被投毒 |
| S5 | 服务端不校验分片摘要，也不重算整文件哈希 | `mergeChunk` | 合并结果和 `hash` 可以对不上，秒传索引被污染 |
| S6 | 大小、类型只看客户端字段：`size` 原样入库，`mime_type` 取客户端，`ext` 只比白名单不嗅探文件头 | `mergeChunk` | 改扩展名即可绕过类型限制；无单文件上限 |
| S7 | 收到「最后一片」即合并，不检查是否全部到齐（缺片才在合并时报错） | `uploadChunk` | 并发上传时最后一片先到会提前合并失败 |
| S8 | 没有过期清理：中断的 `.chunk` 永久留盘 | 全文无清理 | 磁盘被耗尽 |
| S9 | 只支持本地：`storage_mode` 写死 1，配置了 OSS/COS/S3 也不走 | `mergeChunk` | 多实例部署分片散落在不同机器 |
| S10 | 前端只支持顺序上传、MD5（弱哈希）、取消只是前端停发 | `index.vue` | 无服务端取消，残片靠人工清 |

- 若依 RuoYi-Vue-Plus：OSS 模块用 AWS SDK `S3TransferManager` 做**服务端到对象存储**的分段传输；浏览器侧分片续传见于社区整合文章，官方是否内置**未核实**。

## 三、方案：接口（拟增 `contract/openapi.yaml` 条目，未写入契约文件）

设计取舍：

- 路径资源名 `uploads`（复数名词），动作放末段动词（`complete`），路径参数 `{upload_id}`、`{seq_num}`（命名规范第三节）。
- 传片用 `PUT` + 原始字节体（`application/octet-stream`）：语义天然幂等（同序号重传覆盖），服务端可边收边算摘要，不经 `multipart` 解析临时文件。分片 sha256 放请求头 `X-Chunk-Sha256`（64 位十六进制）。5MB 分片远小于现有 `max_package_size`（101MB），不用改 `server.php`。
- 完成动作走后台任务：受理后任务进 `merging`，前端轮询任务详情直到 `succeeded`（拿到 FileObject）或 `failed`。理由：1GB 合并 + 重算摘要会占住 webman 常驻 worker 数秒到数十秒，同步做会拖慢同进程其他请求。
- 不挂 MCP 工具（二进制传输不适合 MCP 通道）。

请求与响应字段（JSON 小写蛇形，与列同名；雪花 id 一律输出字符串）：

| 形状 | 字段 |
| --- | --- |
| `POST /uploads` 请求 | `original_name`（≤255）、`size_bytes`（≥1，≤上限）、`sha256`（64 位小写十六进制）、`visibility`（`private`/`public`，默认 `private`）、`usage`（可选，同 `POST /files`）；头 `Idempotency-Key` 可选 |
| UploadTask | `id`、`original_name`、`size_bytes`、`chunk_bytes`、`chunk_count`、`received_count`、`received_seq_nums`（详情接口才带，整数数组）、`state`、`expire_time`、`file`（`succeeded` 时为 FileObject，否则 null）、`error_code`（`failed` 时）、`create_time` |
| 传片响应 | `seq_num`、`received_count` |

状态（`state`，字符串 + CHECK）：`running`（接收中）→ `merging`（合并中）→ `succeeded` / `failed`；`running` 可转 `cancelled`（用户取消）或 `expired`（过期清理）。取值待拍板见第七节 4。

## 四、方案：服务端分层与存储

沿用 `server/src` 现有分层，文件域内新增，不建万能基类：

| 层 | 拟新增 / 改动 | 说明 |
| --- | --- | --- |
| `app/controller` | `UploadController`（薄壳，照 `FileController` 写法：取请求、转流、调 Http 组装层、映射异常） | 路由由契约生成 |
| `Application/File` | `ChunkUploadService`（开始、传片、查询、完成受理、取消）；`UploadHttp`（入参校验、权限判定、信封输出，照 `FileHttp`）；`UploadConfig`（分片大小、上限、过期、并发与配额数值） | 合并后的校验与落库**复用**现有 `UploadService` 的嗅探 + 双白名单 + `sand_system_file` 写入，抽出一个共用的「定稿」方法，不复制代码 |
| `Task/Handler` | `MergeUploadHandler`（合并任务）、`ExpireUploadsHandler`（过期清理） | 挂现有 `TaskDispatcher`/`TaskWorker`；任务类型名按 `TaskHandlerCatalog` 现行命名 |
| `Domain/File` | `UploadTask`（只读视图）、`UploadState`（枚举）、`UploadTaskRepository`（接口）、`FileStorage`（存储接口，见下）、`FileException` 补上述错误码工厂 | |
| `Infra/File` | `PdoUploadTaskRepository`（DBAL 仓储，分片登记的 upsert 只走方言层）；`LocalFileStorage` 实现 `FileStorage` 并加分段动作；可选 `S3FileStorage` | |

存储接口（v4 J-12「文件存储加分段五个动作」落地；与 `LocalFileStorage` 注释「不再自定义存储接口」冲突，见第七节 2）：

| 动作 | 本机磁盘驱动 | S3 兼容驱动（可选） |
| --- | --- | --- |
| 开始 | 在存储根下建任务目录 `parts/<upload_id>/`（`upload_id` 为纯数字，格式校验） | `CreateMultipartUpload`，`UploadId` 存任务表 `driver_upload_key` |
| 传片 | 边读请求体边算 sha256 写 `parts/<upload_id>/<seq_num>.part.tmp`，校验通过后原子改名为 `<seq_num>.part`（同序号覆盖） | 校验通过后 `UploadPart`（分段号 = `seq_num + 1`），ETag 存分片表 |
| 列已传片 | 以分片表为准；目录只用于对账 | 以分片表为准；`ListParts` 用于对账 |
| 完成 | 后台任务按序号流式拼接到随机 32 位对象键（复用 `writeStream`），边拼边算整文件 sha256，再删任务目录 | `CompleteMultipartUpload`；整文件 sha256 需回读对象流式计算（内网流量成本，见第七节 3） |
| 取消 | 删任务目录 | `AbortMultipartUpload` |

数值（配置项，进 `config/file.php`；建议名按命名规范「数量带单位」，与 v4 T-7 的建议名 `upload.chunk_size` 等略有出入）：

| 配置键（建议） | 默认 | 约束 |
| --- | --- | --- |
| `upload_chunk_bytes` | 5242880（5MB，老板 11-17 定） | ≥ 所用存储最小分段（S3 为 5MiB）；分片数 ≤ 10,000 |
| `upload_max_bytes` | 1073741824（1024MB，老板 11-17 定） | 单文件上限，与 `/files` 的 `max_bytes`（100MB）分开 |
| `upload_expire_hours` | 24（老板 11-17 定） | 自最后一次传片起顺延 |
| `upload_active_max_count` | 3（建议值） | 单用户 `running` + `merging` 任务数 |
| `upload_inflight_max_bytes` | 2147483648（建议值） | 单用户未完成任务声明大小合计 |
| `upload_chunk_rate_per_minute` | 120（建议值） | 单用户传片频率 |

## 五、方案：表结构（**待编号表审批，未建表**）

两张表在《编号两列表-修订》（草稿）里已登记为雪花类；本节只写拟用结构，不出迁移文件、不执行 DDL。连带改动：秒传查询要在 `sand_system_file` 上加索引 `(uploader_id, sha256, size_bytes)`，该表 DDL 不在本仓（见第八节缺的输入）。

分区：v4 按「分片数十万行/月」把 `sand_system_upload_chunk` 列入按月分区。本方案建议**不分区**：分片行在任务完成、取消或过期时即删除，常驻行数只等于在途分片数（上限 = 用户数 × 并发任务数 × 每任务分片数），整月 `DROP` 分区反而会误删跨月在途任务。是否分区见第七节 5；若坚持分区，按 M-14 去掉下方外键、主键改含 `create_time`。

## 六、方案：安全、清理、测试与验收、工作量

### 6.1 安全

| 面 | 做法 | 对应旧版问题 |
| --- | --- | --- |
| 鉴权 | 全部接口走 v1 鉴权链（服务端会话 + 权限码）；任务按 `uploader_id` 隔离，查他人任务一律 `UPLOAD_NOT_FOUND`（不区分「不存在」和「不是你的」，防枚举） | S4 |
| 类型校验 | 三道：初始化比扩展名白名单（早拒）；首片到达后嗅探文件头（早拒，省带宽）；合并后整文件 `finfo` 嗅探 + 扩展名/MIME 双白名单（权威），不通过即删对象、任务 `failed`。白名单与 `/files` 共用一份配置 | S6 |
| 完整性 | 每片 sha256 服务端边收边算，不符拒收不落盘；合并时整文件重算 sha256，与声明不符任务 `failed`；长度按约定精确校验 | S5、S7 |
| 路径穿越 | 客户端值不进任何路径：任务号是服务端雪花 id、序号是范围内整数、对象键服务端随机生成；存储键格式校验（`parts/<数字>/<数字>.part` 与现有 `^[a-f0-9]{32}$` 两种模式）；沿用 Flysystem `DISALLOW_LINKS`；原始文件名只经 `OriginalName::sanitize` 写元数据；存储根在 web 根外 | S1、S2 |
| 秒传防探测 | 只在同上传人范围内命中；不命中时与正常初始化响应形状一致，不暴露「别人有这个文件」 | S3 |
| 配额 | 单用户未完成任务数、在途声明字节合计上限；本机驱动初始化时检查磁盘余量（`disk_free_space` ≥ 声明大小 × 2，留合并副本空间） | S8 |
| 限流 | 初始化与传片按用户限频，计数放共享存储（Redis/库），超额 `UPLOAD_LIMIT_EXCEEDED`；现有进程内 `WindowRateLimiter` 不能直接复用（多 worker 不合并计数） | — |
| 审计 | 初始化、完成（含结果）、取消写审计；传片只写普通日志 | — |
| 跨实例 | 分片走存储驱动，不落 worker 本地临时目录；本机驱动只在 `instances=1` 声明下允许进生产（v4 J-6 `LocalStateGuard`、S-17） | S9 |

### 6.2 清理任务

- 定时任务 `ExpireUploadsHandler`，默认每小时一次（可配）：
  1. `running` 且 `expire_time` 已过 → 条件更新为 `expired`，调驱动「取消」删分片 / `AbortMultipartUpload`，删分片行；
  2. `merging` 超过合并超时（建议 2 小时，可配）→ `failed`，同上清理；
  3. `cancelled`/`failed`/`expired`/`succeeded` 任务行保留 7 天（可配）后硬删；
  4. 对账：存储里 `parts/` 下没有对应 `running`/`merging` 任务的目录直接删（兜底取消失败、进程崩溃留下的残片）。
- 结果（清了几个任务、多少字节、失败几个）写普通日志；单次处理条数设上限，分批执行，避免长事务。
- 用户取消走同一套清理逻辑，同步执行。
- 对象存储另在部署文档里要求配置桶生命周期规则「未完成分段 N 天后中止」作为第二道兜底（属部署清单，不是代码）。

### 6.3 测试

| 层 | 内容 |
| --- | --- |
| 单元 | 分片数与末片长度计算、上限边界（0、1、恰好上限、上限 +1）、状态迁移表、配置校验（分片大小低于存储下限拒启动）、存储键格式校验、错误码映射 |

### 6.4 验收标准（全部可客观判定）

1. 契约：`openapi.yaml` 新增条目经 `tools/contract-build` 生成路由、权限、错误码、TS 类型与测试骨架，生成物与源一致；错误码先登记再引用。
2. 功能：1024MB 文件在本机驱动下按默认 5MB 分片完成上传，生成的文件记录 sha256 与源文件一致；中途断网/刷新后只补传缺片即可完成。
3. 秒传：同人同文件第二次初始化不建任务、直接返回 FileObject；换一个账号同文件不命中。
4. 安全：6.3 安全用例全部通过；穿越类输入不在存储根外产生任何文件（测试断言存储根外目录无新增）。
5. 清理：构造过期任务后跑一次清理，分片目录与分片行全部消失、日志有记录；对账能删掉无主残片目录。
6. 双库：集成测试 PG 15+ 与 MySQL 8.0+/8.4 均通过；迁移在测试库跑「升级 → 回退 → 再升级」通过。
7. 门禁：PHPStan 最高级别、deptrac、命名自查、eslint/tsc 全过；`server/src` 无新增进程内状态。
8. 内存：合并 1024MB 文件期间任务进程内存峰值不随文件大小线性增长（流式拼接，断言峰值 < 64MB）。
