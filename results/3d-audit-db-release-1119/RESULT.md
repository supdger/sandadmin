# 建库 / DDL / 迁移放行前独立审计（3d-audit-db-release-1119）

- 审计日期：2026-11-19
- 审计性质：只读审计。依据老板 2026-11-19 的规定，审计通过就算批准。
- 审什么：能不能放行在老板 Mac 上为每个任务单独起临时 PostgreSQL / MySQL 实例，开做框架核心里必须建库的工作。
- 怎么做的：全部取证用只读命令完成（git ls-tree / show / grep、shasum、lsof、ps、brew services list）。没有建库，没有启停任何数据库或进程，没有跑迁移，没有改任何仓库文件，没有读 .env、webhook.env、private/。

---

## 结论：有条件放行

可以放行"每个任务一个隔离临时库"的开发和验证工作。下面第 1 节的 9 条前置条件（C1–C9）全部满足之前，任何任务都不许启动数据库进程。放行范围、隔离硬约束、先开哪些工作包见第 2–4 节。第 5 节列出仍须单独拍板的事项，在拍板之前，相关产出只能停在隔离库和功能分支里，不能定稿，也不能合并。

为什么不直接放行：
1. 现行沙箱 `devin-queue/iso-sandbox/policy.sb:44-46` 明确禁止执行 initdb、postgres、pg_ctl、mysqld 等程序，而且没有允许起库的版本。不改策略，任何受沙箱约束的任务都起不了库。
2. 本机有三条路会让任务误连老板已有的库（见第 6 节的 R1、R2），必须先在策略层堵死。
3. 基线 0001–0003 还没进仓。"0001 算不算已发布"在仓库和设计文档里说法互相矛盾。

为什么不判不可放行：
- 编号表已经批准，hash 核对一致。
- 建库这条链的根是迁移执行器和账本，设计已经写定（v4:217-221、392-398、525-530）。
- 基线草稿有唯一、可追溯的来源。
- 隔离方案本身合理，现有沙箱已经验证过端口段 19100–19199 的放行和禁止规则（VERIFY-1118 26/26 PASS）。

剩下的缺口都能用前置条件约束住，不需要先等老板逐项再表态。

## 2. 放行范围

**放行的：**
- 在本机按 C1–C9 为每个任务起独立的临时 PG 18.4 和/或 MySQL 8.4.13 实例，在实例里建库、执行 DDL、跑迁移（包括"升级 → 回退 → 再升级"）、跑需要真库的 Integration 测试、用 pg_dump / mysqldump 演练恢复点。只在实例内部生效，任务结束销毁。
- 在功能分支上写迁移文件、执行器、账本、方言层等源码。提交是否授权，按每个任务自己的授权判断；本审计不授权 push。

**不放行的（仍须单独获批或另走审计）：**
- 合并任何 PR，push main，打 tag，发布。
- 动老板已有的 postgresql@18 服务或数据目录、`/usr/local/mysql` 实例、brew `mysql@8.4` 的默认数据目录 `/opt/homebrew/var/mysql`。
- 动 wf-install-1117 现场（不启动、不清理、证据保留），以及 final-runtime-check-1112 的残留 PG。
- 用 Docker 容器起库。本审计只审了"本机程序 + 独立数据目录"这一种方案。
- 云端库、共享库、任何非本机的库。
- 把还在等老板审的表（第 5 节 P4）写进基线定稿。

## 3. 建库前置核查结果（审查项 1）

1. **编号表：齐。** `编号两列表-修订.md` 的 sha256 是 `0e12a087ee95d0365c25f02ddab85686891c7ec49001da8f927938807ecd7396`，和批准版一致。表数 210：框架 47、SandIAM 26、SandAI 137；按编号方式分，自增 68、雪花 142，分段小计核过。批准原话（`idlist-approved-sync-1118-readonly/README.md`，11-18 08:34 PST）："批准这版210张逐表编号归类，仅限编号表，不包含启库、DDL、迁移、合并或发布。"本审计补上的正是"启库、DDL、迁移"这一块，合并和发布仍未授权。
2. **基线 0001–0003：没进仓。** sandadmin main `977427a` 只有 0004–0007，全部历史和本机 7 个分支里都查不到 0001–0003。sand-core / sand-package 的所有分支里也没有。草稿只在 `1x-ddl-1110/out/migrations/`。仓库里的文档自相矛盾：`backend-structure.md:12` 说"基线文件必须齐全"，`AGENTS.md:14` 又说"本仓无 migrations"。所以"基线入仓"本身就是第一批工作包（B5），不是放行的前提；但入仓时必须按 C7 从唯一来源拷贝。
3. **"0001 算不算已发布"：口径不统一，这是硬缺口。**
   - 仓库这边：`0004_*.sql:5`、`0005_*.sql:4` 写"不改已发布的 0001"；`RELEASE-NOTES-0.2.4.md:42` 写 0004–0007 已随 0.2.4 发布。
   - 设计这边：`鉴权P0-v4.md:177`、`:977` 写"基线未发布，直接改列定义"；v4:1283、1401 写"基线定稿前定"。
   - 事实：仓库里根本没有能执行这些迁移的执行器，0001 也不在仓。所以 0.2.4 的"已发布"只是文件随 tag 公开，没有任何环境是由执行器按账本跑过 0001 的（只读取证范围内没找到反例）。
   - 审计意见：由技术总监统一为"0001–0003 未发布、未定稿，可以直接改；0004–0007 视情况并进基线或保留为增量"，同时改掉 0004/0005 头注里的"已发布"字样。这条记为 C8，不挡隔离库开工，但挡基线定稿和合并。
4. **迁移执行器与账本：设计齐了，代码还没有。**
   - 设计：v4:217-221、392-398、525-530 规定：一套执行器；账本 `sand_system_schema_migration` 每条连接一本、按命名空间记账；每条连接一把迁移锁（PG 用 advisory lock，MySQL 用 GET_LOCK）；账本校验对不上的半成品库拒绝继续；每份迁移带回退脚本，但生产环境不执行回退；拿不到恢复点就拒绝迁移；只走 CLI。
   - 现状：sandadmin 仓里没有执行器代码。sand-core 实际在用的是另一套简化版：`bin/sand migrate` + 账本 `sand_schema_migration`，只有 `filename, applied_at` 两列，没有校验和、没有锁、只支持 PG（`DatabaseInstaller.php:97-150、115-119、218`）。v4 要求把它和 SandAI 的私有账本一起废掉、收编进新执行器。
   - 文档缺口：账本的列结构 v4 没写，统一账本有没有 checksum 列也没写明。建议在 B4 工作包开头先由技术总监补一页账本列结构（至少包括 namespace、version/filename、checksum、applied_time、release_version、execution_ms）再开写；可以参照 sand-package `ExistingSchemaManifest.php:74-83` 已经在读的那组列名。
   - 回退脚本：v4:398 要求每份迁移带回退脚本，但 0004–0007 和基线草稿都没有回退文件。B4/B5 需要补上（基线本身可以不带）。
5. **隐式建库风险：可控。** 三个仓的 main 上都没有真正的 `CREATE DATABASE`。sand-core 的执行器明确不建库（`:617-618` 报"请先创建"）。要注意两个会碰库的入口：一是 composer 的 post-install 会调 `support/sand-publish.php:28` 里的 `Install::install()`，包级 Install 只发布文件，但插件的 InstallLogic 会执行 install.sql；二是 Integration 测试会直接 CREATE / DROP 夹具表。这两条都必须在只连临时实例的前提下才能跑（C4、C9）。

## 4. 隔离方案是否合规（审查项 2）

方案本身合规，但按现状不能直接落地，要先补 C1–C3：
- **不碰老板已有服务：** postgresql@18（pid 70832，127.0.0.1/::1:5432，数据目录 `/opt/homebrew/var/postgresql@18`）由 brew LaunchAgent 常驻。方案用 `pg_ctl -D <任务目录>` 起独立实例，不经过 `brew services`，不碰它的数据目录。现有策略已经禁止读写这个目录，新策略保留即可。
- **不碰 wf-install-1117：** 现场在 `~/agent-work/grokbot/wf-install-1117/`（pgdata 74M、work 733M、evidence、两个 zip），当时用的端口是 25433、18787、12206，目前没有进程在跑。现有策略禁止读写整个目录，新策略必须保留。本审计只读了它的记录文件，没有进 pgdata。
- **只监听 127.0.0.1 + 端口 19100–19199：** 网络层由沙箱强制，已验证过（绑 19111 成功、绑 19099 和 5432 被拒）。配置层由 C3 保证，MySQL 一定要关掉 mysqlx。
- **独立数据目录 + 结束销毁：** 由 C4、C6 保证。
