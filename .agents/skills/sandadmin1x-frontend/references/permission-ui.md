# SandAdmin 1.x 权限显隐与鉴权页面流程（草稿）

适用范围：菜单/按钮/路由显隐、登录、点选验证码、找回密码、双因素、sudo 再验证、强制改密、首次设置、开发免登录入口。所有流程的状态机和判定都在服务端，前端只做展示、搬运和用户交互——前端不得自己判定「账号存不存在」「验证码对不对」「权限该不该给」。

## 一、权限显隐

### 1.1 数据来源

- 登录建立会话后，菜单树取 `GET /me/menus`，权限码集合随会话/`/me` 面下发（具体字段以契约为准）。
- 权限码格式 `<域>:<资源>:<动作>`（如 `system:user:read`），判定用「集合里有没有这个码」，前端不得拼字符串猜、不得按角色名/用户名/`id === 1` 特判。
- 超管（`is_super`）由服务端判定并在下发信息里给出，前端只消费结果。

### 1.2 三层显隐

| 层 | 做法 |
| --- | --- |
| 菜单 | 侧边栏/导航只渲染 `GET /me/menus` 返回的节点，不渲染本地全量菜单再过滤。 |
| 路由 | 路由守卫比对页面所需权限码与集合；无权限直达 URL 显示 403 页，不白屏、不静默跳首页。 |
| 按钮/操作 | 新增、批量删除、行内编辑/删除、导出等操作按权限码显隐（默认隐藏；禁用态只在需要给用户「看得见点不了」的语义时用）。 |

按钮级判定双轨机制（已定，总监 11-17）：`usePermission()` hook 给逻辑判定（要不要禁用、要不要发请求），`<Permission code>` 包装组件给 JSX 包裹显隐，内部都查会话权限码集合；路由配置上加 `permission` 字段供路由守卫用。默认隐藏，不用默认禁用。

### 1.3 硬规矩

- 显隐是体验层，不替代鉴权：无权限接口被调时按契约错误码正常报错，页面不崩。
- 数据范围（本人/本部门/全量）由服务端过滤，前端不做、也不能做客户端过滤充数；无数据就渲染空态。
- 新增「返回他人数据」的页面入口时，对应接口必须在受限清单登记（后端门禁），前端在联调前确认该接口已在契约里，不调没登记的接口。
- 插件菜单/路由只从内核扩展点声明的产物进入 `/me/menus` 和路由表，前端不接受任何「前端自己注册菜单」的写法。

## 二、登录页与点选验证码

### 2.1 流程（前端只负责编排顺序）

```
登录页输入账号密码
  →（服务端要求时）GET /auth/captcha 取点选挑战图
  → 用户按目标顺序点击 → POST /auth/captcha/verify 提交坐标
  → POST /auth/login（携带挑战/票据字段，按契约）
  → 成功：Cookie 会话建立，跳目标页
  → 已开双因素：进入第二因子页（见第四节）
  → must_change：进强制改密页（见第五节）
```

### 2.2 硬规矩

- 点选组件已有 `web/src/pages/auth/ClickCaptcha.tsx`：提交坐标必须按显示缩放比换算回服务端原图坐标系（高分屏/缩放/移动端显示像素 ≠ 原图像素），且保持用户点击顺序不乱序。
- 验证码何时出现由服务端响应决定（失败计数/限流触发），前端不维护「错几次弹验证码」的本地计数。
- `login_ticket` 是一次性服务端凭据，前端只透传，不持久化、不读内容、不信任自己算的 `verified` 类字段。
- 登录、锁定、限流、找回的提示文案一律用服务端 `message`，前端不自己编造（防枚举口径要求同文案同耗时，前端多嘴就泄密）。
- 响应体永不含 token；登录成功只表现为会话 Cookie 已种下，前端不检查 Cookie 内容（HttpOnly 也读不到）。
- 登出调 `POST /auth/logout`，清本地页面状态回登录页。

### 2.3 会话期间的行为

- `401`（会话失效/`SESSION_EXPIRED`）：清页面态 → 登录页，带回来地址；提示用服务端 message。
- `403`：403 页或操作提示，不当登出。
- `503 + Retry-After`（会话存储故障）：显示「稍后重试」类提示并按秒数重试，不踢回登录页、不清用户输入。
- 「记住登录」1.0 不做（已定，总监 11-17），前端不做该 UI；将来若做，按 v4 单独设计、不覆盖管理员和高权限。
- 空闲/绝对有效期由服务端判（普通账号与管理员分档，具体值以服务端为准），前端不做本地倒计时踢人。

## 三、找回密码（忘记密码）

### 3.1 入口显隐

- 登录页「忘记密码」入口必须按 `GET /auth/recovery/capability` 返回的可用渠道决定：短信和邮箱都没配时隐藏入口；只配一种时只给该渠道。
- capability 查询是公开接口，登录前可调；渠道清单以响应为准，前端不猜。

### 3.2 流程

- 短信渠道：`POST /auth/recovery/sms-codes` 申请 → 填 6 位码 → `POST /auth/recovery/verifications` 校验（只验不消耗）→ `POST /auth/recovery/password` 提交新密码。
- 邮箱渠道：`POST /auth/recovery/email-links` 申请 → 邮件链接落地页打开时先 verifications 校验 → 同上提交。
- 找回路径族用鉴权稿 `/auth/recovery/*`（已定，总监 11-17）；架构稿 K-2b 已同步改为同一族，旧 `/auth/password/forgot|verify-code|reset` 作废（`/auth/password/force-change`、`/auth/password-policy` 不受影响）。

### 3.3 硬规矩

- 防枚举：申请结果的展示文案固定用服务端返回（「如果该账号存在……」），前端不得根据响应差异加「账号不存在」类提示。
- 错误计次、人机验证触发、递增等待、锁找回通道都由服务端管；前端收到对应错误码按 message 展示，不本地计次。
- 重置成功后不自动登录：提示成功 → 跳登录页让用户用新密码登录；已开双因素账号照过第二因子，前端不得提供「找回后免验证」路径。
- 找回页/邮件落地页不往 URL、日志、分析工具里放令牌明文；提交时走请求体。
- 改联系方式（`POST /me/contact`）是高危操作，触发 sudo 弹窗（见第五节），不做成普通表单直提。

## 四、双因素（2FA）

### 4.1 登录第二因子页

- 密码通过后服务端返回「进入第二因子」挑战态（`mfa_ticket` 一次性凭据，5 分钟）：前端切到第二因子页，提交 TOTP 码或恢复码其一，通过后才算登录完成。
- 平台后台第二因子只有两种：TOTP（Google Authenticator 类扫码）或恢复码；短信不作第二因子，短信只用于找回密码。具体可用方式由服务端按账号绑定情况下发；双因素后台开关默认关，开关打开后由管理员设「全站要求绑定」或「按角色要求绑定」，要过等保三级的部署必须打开。前端一律按服务端下发的可用因子和 `must_enroll_mfa` 标记渲染，不硬编码谁必须开。
- 用恢复码登录成功后，服务端会要求强制重新绑定：前端进重绑流程页，不允许跳过。

### 4.2 绑定/管理页

- 绑定页展示 `otpauth://` 二维码 + 手动输入密钥的备选，确认绑定需提交一个有效 TOTP 码。
- 恢复码只在绑定成功时完整显示一次，页面必须明示「只显示这一次，请保存」；之后界面只显示「已生成/剩余数量」类状态，不提供再次查看。
- 解绑、重置、强制标记（`must_enroll_mfa`）等管理操作全是高危 → 走 sudo 弹窗；高权限账号重置需双人复核的交互按服务端流程配合展示。

## 五、sudo 再验证与强制改密

### 5.1 sudo 弹窗（全局唯一实现）

- 高危接口在 sudo 窗口外被调时返回契约错误码（码名 `SUDO_REQUIRED`；已定，总监 11-17）：统一 request 封装捕获后打开全局 sudo 弹窗（重输当前密码；账号有 MFA 时优先第二因子，按服务端要求）。
- `POST /auth/sudo` 验证成功后重放原请求；窗口长度前端不硬编码（10 分钟；已定，总监 11-17），每次高危操作都以服务端判定为准。
- sudo 弹窗只有一个全局实现：页面/插件禁止自己渲染密码输入框、禁止插件页面把高危调用包装成别的接口转嫁再验证。

### 5.2 高危操作清单（会触发 sudo 的调用面）

改超管、角色权限变更、分配/移除角色、插件启停/卸载/删除、全量导出、安全设置（含会话时长、日志留存）、系统更新、签发/吊销机器令牌、代登录、代人重置双因素、改联系方式、解除 require_reset/组合锁、未编译版网页提交插件申请等——清单以后端为准，前端不用维护第二份。

### 5.3 强制改密（must_change）

- 登录后账号处于 `must_change`（含临时密码首次登录、require_reset 重置后）时进入强制改密页，此时只有放行清单可用：`/auth/password/force-change`、`/auth/logout`、`GET /me` 系列——前端在改密完成前不放开其他路由/菜单。
- 密码规则（长度、弱密码要求）从 `GET /auth/password-policy` 取，不在前端写死一份规则。
- 改密成功会轮换会话并踢掉其他会话：前端跳回正常首页/目标页即可，不做「保留旧页面态」的处理。
- 密码定期更换是后台开关、默认关：前端不主动加「密码到期」逻辑，到期强制走 must_change 同一通道即可。

## 六、首次设置与开发免登录

### 6.1 首次设置（/setup）

- `/setup/*` 走 bootstrap 会话三步端点（`state/password/site`，以契约为准）；完成后端点永久 `410 Gone`：前端收到 410 后隐藏设置入口、不再重复请求。
- 设置页只在安装/初始化场景可达，不做成常驻入口。

### 6.2 开发免登录（dev-login）

- dev-login（即开发免登录）是开发构建专用：前端调用点集中放一处（现状在 `web/src/api/auth.ts` 的 dev-login 调用），随后端 dev 链按 `SAND_DEV_BUILD` 编译期整条剔除——前端代码组织必须保证剔除后无残留调用（构建产物 grep 零残留是发版门禁）。
- 生产构建里不得出现任何 dev-login/免登录入口、探测调用或「开发模式跳过登录」分支。
- 真实登录闭环（R20）验收通过前，不得宣称「登录可用」；mock 登录态只服务开发联调。

## 七、前端通用安全红线（复述，便于检查）

- 不持久化令牌、不读 HttpOnly Cookie、不拼 Bearer。
- 页面内容遵守 `default-src 'self'` 起步的 CSP；不引入外站脚本/图片域，确实需要时提出来改 CSP 配置而不是绕。
- 不把令牌、密码、验证码、Ticket 写进 URL、console、日志上报、分析工具。
- 防枚举面（登录、找回、验证码）只用服务端文案，不加戏。
