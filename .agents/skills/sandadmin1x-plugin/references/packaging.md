# 插件打包、分发与安装

分发模型按 v4 定稿：**独立仓库 + zip 包 + catalog.json 元数据 + 真实签名**整体保留；老模型里"网页在线拉包安装到生产"整条废弃。本稿写包怎么打、怎么发、怎么进宿主、怎么验收。

## 1. 分发模型总览

- 权威源 = 插件**独立仓库的已提交修订**。发行 zip 必须从已提交修订构建。
- `catalog.json`（宿主仓库根）只做插件市场的**元数据来源**：插件身份、版本、kernel_api 兼容范围、资产名、SHA-256、签名校验信息。**下载动作发生在打包/部署侧，不在生产实例上**。
- 环境分轨：
  - **编译版/生产**：插件动作只有查看、启用、停用。没有安装、没有升级、没有网页通道（相关路由 404）。
  - **未编译版（开发/构建环境）**：安装/升级走离线包 + CLI；另有一条受限网页申请通道（见第 5 节）。
- 「未编译」判定看构建产物 manifest 的 `build_kind` 字段，不看入口文件形态。

## 2. 发行包（zip）内容契约

zip 根目录必须包含：

| 内容 | 要求 |
| --- | --- |
| 清单 `manifest.json`（已定，总监 11-17） | 字段见 contract.md 第 3 节 |
| `README.md` | 安装器可渲染的说明文档 |
| `migrations/` | 声明式迁移序列，覆盖 PG 与 MySQL 两库 |
| 后端源码 `server/`（已定，总监 11-17） | PHP 源码，不含 `vendor/` |
| `web/` 前端源 | React + Semi 源码，不含 `node_modules/` |
| lockfile | `composer.lock` / `pnpm-lock.yaml` |
| SBOM | CycloneDX 1.5+ JSON，随包签名归档 |

禁止出现在包里：`vendor/`、`node_modules/`、`install.sql`/`update.sql`/`uninstall.sql`、安装器/更新器/终端脚本、任何"解包即执行"的入口。

## 3. 签名与来源证明

- 签名算法建议 **Ed25519**。`signature_verified` 必须是真验签结果：验签失败一律拒绝；禁止硬编码 `true`；未实现真验签前字段如实标"仅 sha256 完整性校验"，不许写"已通过"。
- 编译版（生产）**完全禁止"未签名包 + 显式参数安装"**；该口子只留开发环境。
- 信任根：验签公钥编进内核发行包、随内核制品签名，后台界面不可改；客户自有公钥只能经 CLI 加进本地白名单，加入动作记审计。
- 私钥：发布私钥离线保管或 HSM/云 KMS，专人保管；CI 只拿签名接口、拿不到私钥；签名动作双人复核。
- 轮换与吊销：每个签名带 key id、多密钥并存；吊销列表随内核更新下发；新公钥随版本下发并存一段窗口期，旧私钥停用即吊销。
- 制品只由 CI 在 tag 触发时构建（来源证明 + SHA-256 校验和 + SBOM + 验证方法随发布附出）；**个人电脑上打的包不发布**；安装闸除 Ed25519 验签外再校验来源证明。

## 4. catalog.json 条目

- 条目内容：受约束的仓库标识（`owner/repo` 形态）、不可变 tag、精确资产名、版本、kernel_api 兼容范围、SHA-256、签名校验信息。
- 前端只能选插件和版本，**不提交、不覆盖下载地址**；由服务端取 catalog、校验仓库语法、推导下载地址、下载、验 digest 与签名、校验包身份与版本后，才进暂存。
- catalog 仓本身可变，但每个被选中的包由「仓库 + tag + 资产 + 版本 + digest」钉死；验收要记录宿主实际加载的 catalog 修订——分支名或 push 成功不算证明。
- 下载包或读 README **不产生任何副作用**：不执行 SQL、不部署运行时文件、不创建已装注册。

## 5. 安装通道（双轨）

- **生产/编译版**：只有查看、启用、停用。安装与升级在生产不存在。
- **离线包 + CLI**：标准安装/升级路径，内核 PackageOps 执行，与生命周期账本同一套幂等记录。
- **未编译版网页申请通道**（开发/构建环境）：HTTP 层只做一件事——登记 `sand_system_lifecycle_request`；解包与执行由独立生命周期进程做，网页进程不解包、不执行命令。五个硬条件缺一不可用：
  1. 仅平台后台超管（不是普通管理员）；
  2. 先验签名再解包，验不过直接拒绝；
  3. 提交动作强制二次验证（纳入高危操作清单）；
  4. 接口绝不暴露公网（内网 + 网络层限制，登录态保护不算数）；
  5. 默认关闭，要用显式打开。

## 6. 安装闸（装进来之前内核要查的）

1. 验签 + 来源证明 + SHA-256 一致性；
2. `kernel_api_min`/`kernel_api_max` 语义化区间检查；
3. `databases` 与目标库匹配检查；
4. 插件间依赖满足检查；
5. 依赖审计：对包 SBOM 跑漏洞扫描，High/Critical 拒装（例外须平台管理员签到期日）；
6. 前端依赖白名单检查（插件前端依赖只用宿主共享白名单）；
7. 已装插件每天随宿主复扫依赖漏洞，命中新高危进内核维护的「插件版本拒启用清单」（随发行包更新）。

## 7. 交付流程（继承老底稿、按新契约精简）

1. **冻结边界**：插件标识、表前缀、命名空间、路由前缀、权限码、kernel_api 区间、`databases`、扩展点清单、依赖插件、错误/DTO 契约——写下来再动手。
2. **源头实现**：插件代码、前端源、manifest、migrations、README、测试都在插件仓完成。
3. **静态/包验证**：语法、类型、双库迁移静态检查、包完整性、依赖审计。只算静态/包证据。
4. **提交发版**：审 scoped diff、提交插件仓、CI 从该修订构建 zip、签名、重新下载校验 digest 与签名。
5. **更新 catalog**：仓库、tag、资产、版本、kernel_api 范围、digest、签名信息写进条目。
6. **隔离环境安装验收**：见第 8 节。
7. **宿主侧证据单独提交**：catalog、兼容矩阵、验收材料与插件证据分开提交，不混为一条结论。

## 8. 安装验收与证据分级

安装验收最小集（在未编译/开发环境的隔离宿主里做）：

1. 干净零插件宿主先确认能装、能登、能做基础管理；
2. 装插件：加载状态、菜单、权限到位；
3. 跑通一条核心业务路径；
4. 从真实旧版本升级到目标版本（同版本空迁移不算升级）；
5. 卸载：按所选数据处理口径（保留/导出后删/直接删）核到文档所写的清理状态；
6. 卸载后宿主仍能启动、登录、提供基础管理。

证据分级——每个结论只能挂它够得着的级别：

| 级别 | 含义 |
| --- | --- |
| 静态 | lint、类型检查、迁移静态检查、包完整性 |
| 包 | 清单与包内入口能独立解析或执行 |
| catalog | 仓库/tag/资产/digest 一致解析，无客户端可控地址 |
| 安装 | 隔离宿主里实际装上的插件行为 |
| 部署 | 复制或安装进目标环境 |
| 生产 | 仅限用户授权、外部可观察的结果 |

- 发行资产 + SHA-256 只证明**包身份**，不证明安装、升级、运行行为。
- 浏览器里看到插件卡片/版本详情是**界面观察**，不是安装证据。
- 影响信心或回滚路径的失败尝试与残留清理证据要保留，不丢。

## 9. 老分发模型哪些没继承（摘要）

| 老条款 | 处理 |
| --- | --- |
| `info.ini` 状态机当账本 | 废弃 → 状态记 `sand_system_plugin` 表 |
| `install.sql`/`update.sql`/`uninstall.sql` 三件套 | 废弃 → `migrations/` 声明式序列，内核执行器执行 |
| `host_min` 单版本号 | 废弃 → `kernel_api_min`/`kernel_api_max` 语义化区间 |
| 网页在线拉 GitHub Release 装到生产 | 废弃 → catalog 只出元数据，生产不安装 |
| 网页上传 zip 直接执行包内 PHP/SQL、网页终端 | 废弃（上游公开 RCE 报告的攻击面） |
| 浏览器拼包地址安装 | 废弃 → 前端只交插件身份与版本 |
| 插件私有迁移台账/私有执行器 | 废弃 → 收进内核执行器与 `sand_system_schema_migration` 一本账 |
| 聚合仓迁移/退役流程 | 废弃 → 属 0.x 历史材料，不进 1.x 契约 |
| 共享版 Composer 基础包消费链（sand-core/sand-package 发版验收 6 步） | 废弃 → sand-package 下线、sand-core 降级为旧兼容层；1.x 不发公共 Composer 基础包、插件 SDK 随宿主内核版本提供（已定，总监 11-17） |
| catalog 的 legacy fallback 条目 | 废弃 → 不为恢复聚合仓依赖留 fallback |
