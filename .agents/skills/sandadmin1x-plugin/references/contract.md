# 插件契约：目录、注册、权限、生命周期与能力边界

适用范围：SandAdmin 1.x 插件从写代码到装进宿主全过程要遵守的框架约定。打包、签名、分发通道的细节见 packaging.md。

定稿状态：本稿按 v4 顶层架构 + 老板 8 条规矩 + 11-17 拍板结论修订。标「已定（总监 11-17）」的条目为技术总监 11-17 采纳建议后的定稿值。

## 1. 插件是什么

- 插件 = **独立仓库 + zip 分发 + catalog.json 登记 + 真实签名**的功能包，给宿主内核补业务能力。这个分发方式 1.x 保留。
- 信任模型一句话：**插件是完全受信代码，等同内核**。安全只靠签名、来源白名单、代码审查；没有插件沙箱，也不许对外暗示有。
- 内核不得对任何一个具名业务插件产生运行时依赖；也不许把插件的领域能力塞进内核图省事。

## 2. 仓库与目录结构

- 每个插件一个**独立权威仓库**。装进宿主后落在 `server/plugin/<app>/` 的目录是安装产物（`.gitignore` 内、非源码权威），不是第二权威源，不与仓库同步改。
- 发行 zip 必须从某个**已提交修订**构建，不从不明工作区打包。
- 仓库与包内结构约定：

| 位置 | 内容 | 约定 |
| --- | --- | --- |
| 仓库根 | 清单 manifest | 插件对框架的总声明，字段见第 3 节。`manifest.json`、JSON 格式（已定，总监 11-17）；老契约 `info.ini`+`config.json` 两件作废 |
| 仓库根 | `README.md` | 必带；安装器渲染用的说明文档 |
| `migrations/` | 声明式迁移文件序列 | 覆盖 PG 与 MySQL 两库；命名按迁移规范；内容只允许动本插件前缀的表（见第 8 节） |
| `server/` | PHP 业务代码 | 后端源码目录用 `server/`（已定，总监 11-17），与宿主 `server/`+`web/` 结构同构；`Sand<Plugin>` 命名空间不变；TypePHP 硬规矩（见第 11 节） |
| `web/` | 前端源码 | React + Semi Design 单栈；构建期集成（见第 9 节） |
| 仓库根 | lockfile | `composer.lock` / `pnpm-lock.yaml` 必带入库 |
| 包内 | SBOM | CycloneDX 1.5+ JSON，随包签名归档 |
| `tests/` | 插件测试 | 必带；走分支与门禁（见第 12 节） |

- 包内禁止出现：`vendor/`、`node_modules/`、安装器/更新器/终端脚本、`install.sql`/`update.sql`/`uninstall.sql`、任何"解包即执行"的入口。

## 3. 清单（manifest）契约字段

清单是插件对框架的总声明。清单文件为仓库根的 `manifest.json`（JSON 格式；已定，总监 11-17）——JSON 有 schema 可校验、前端也能读，与 `catalog.json` 同风格。字段口径按 v4 已定内容整理；仍待定的字段以「建议」标注。

| 字段 | 是否必声明 | 说明 |
| --- | --- | --- |
| 插件标识（app） | 必 | 连字符小写（形如 `sand-foo`）；与表前缀、命名空间、迁移命名空间、权限码域段一致 |
| `version` | 必 | 语义化版本 |
| `kernel_api_min` / `kernel_api_max` | 必 | 兼容的内核 API 区间，按语义化版本校验；主版本变化即不兼容。替代老契约 `host_min` |
| `databases` | 必 | 声明支持的数据库。默认要求双库（`pgsql` + `mysql`）——双库是框架对代码的要求，不构成对单个插件部署目标的强制；只支持一种就如实写（如 SandAI 仅 `pgsql`），装到不支持的目标库被安装闸拦截 |
| `frontend` | 有前端时必 | 声明前端入口模块与路由前缀，供宿主 `web/` 构建期收集 |
| `migrations` | 有迁移时必 | 声明迁移目录与序列，内核执行器按此收集执行 |
| 扩展点声明 | 按需 | 菜单、设置分类、定时任务、搜索来源、工作台卡片、文件使用登记、通知来源、停用前检查、用户交接——见第 4 节 |
| `requires` 插件间依赖 | 按需 | 对象形态 `{ "插件标识": "semver区间" }`（已定，总监 11-17），安装闸按语义化区间解析（与 `kernel_api_min`/`max` 同一套区间口径），不满足拒装 |

## 4. 注册与发现：扩展点是唯一入口

- 插件接入宿主**只走内核扩展点**（ExtensionManifest）。清单里声明什么宿主挂什么；没声明的没有。
- 已定扩展位：**菜单、设置分类、定时任务、搜索来源、工作台卡片、文件使用登记、通知来源、停用前检查、用户交接、MCP 工具注册**。
- 每个扩展点契约固定写四项：RequestContext 怎么进、必声明的权限码、宿主二次过滤怎么做、sudo/审计要求。
- 「用户交接」「停用前检查」两个扩展点的契约四要素（输入、输出、可否否决、审计落点）如下（已定，总监 11-17）：
  - 「用户交接」：输入 `{操作者, 移交人, 接收人, 交接范围}`；输出 = 可交接对象清单 + 执行结果；同步调用，插件可否决并给原因。
  - 「停用前检查」：输入 `{插件标识, 操作者}`；输出 `{可否停用, 阻断原因清单}`；有阻断原因时停用流程拒绝并展示原因。
- **定时任务专项**：清单声明 handler；库里只存已登记任务编号和参数（参数过 schema 校验）；**库里不存可执行目标**（不存类名、不存命令行）。
- 禁止的隐式接入方式：
  - 用 SQL（含迁移文件）往 `sand_system_menu`、`sand_system_role_menu` 或任何内核表插行登记菜单与授权；
  - 扫目录自动注册；
  - 在路由/中间件配置里挂旧鉴权中间件（`CheckLogin`/`CheckAuth`）。
- MCP 双向做在框架层（老板规矩第 4 条）：插件经扩展点向框架 MCP 服务注册自己的工具，权限、审计、令牌全用框架同一套；插件要调外部 MCP 用框架的客户端接口，不经框架客户端私自出网。扩展点声明面即 MCP 可查面——插件经扩展点声明的菜单、权限码、路由、接口注册纳入框架 MCP 服务的可查询面；插件不得绕开扩展点私开未登记的管理接口。
- MCP 工具口径（M-02/M-03/M-04）：插件的 MCP 工具在包内 OpenAPI 片段上以 `x-mcp` 声明三档（`read` 只读直执 / `write` 普通写必带幂等键 + `dry_run` / `high_risk` 高危写只生成待确认请求由人 sudo 批准），构建期统一收集进框架 MCP 工具表、不能手写登记绕过；机器令牌任何 scope 不能直执高危档。**租户数据类工具一期不经框架 MCP 暴露**（M-04：框架 MCP 只认宿主机器令牌/内核会话，挂上租户数据工具等于让平台账号跨租户读数据）；插件面向产品用户的 MCP 入口将来另设、经 SandIAM 令牌认证，属插件内容不是框架面。

## 5. 命名与表前缀

- 表名：`sand_<插件词干>_<单数名词>`，同一个插件词干全表一致；去掉前缀后 ≤3 个词、≤30 字符。例：`sand_foo_record`。
- 权限码：`<域>:<资源>:<动作>`。域段 = 插件词干全称、含 `sand_` 前缀（如 `sand_foo:record:read`；已定，总监 11-17）——与表前缀 `sand_<词干>_*`、命名空间同根，防撞且不混宿主 `system:` 域；权限码总表登记进 api-conventions.md。
- PHP 命名空间 `Sand<Plugin>`；插件标识 `sand-<plugin>`（连字符）。插件后台接口统一挂 `/api/admin/v1/plugin/<name>/...` 前缀（已定，总监 11-17）——复用 v1 组同一套鉴权链、限流与审计，`plugin/` 段做命名空间隔离，构建期生成路由表时可断言无冲突。
- 列名、布尔、时间、状态、索引前缀（`uk_`/`ix_`/`fk_`/`ck_`）、枚举小写蛇形——与宿主同一套《命名与注释规范》，不另起一套。
- 时间字段强制 `*_time` 后缀、`datetime` 类型；审计三件套 `create_time`/`update_time`/`delete_time`。禁 `*_at` 和 int 时间戳。
- **主键编号**（老板规矩第 1 条，插件表同样遵守）：数量可预见有限的表（字典、配置类）用 `int` 自增（PG `GENERATED BY DEFAULT AS IDENTITY` / MySQL `AUTO_INCREMENT`）；不可预见持续增长的表用雪花 64 位 `bigint`（41 位毫秒 + 13 位节点 + 9 位序列，应用层发号），接口输出字符串防 JS 精度丢失；nanoid 只用于对外不可猜的链接（文件下载、分享），单独一列、不当主键；外键与被指向主键同型。

## 6. 身份与权限

- **后台管理页**（平台后台身份）：内核会话 + v1 权限码。插件不得另开登录链、不得自带会话/权限/用户表。
- **产品侧接口**：走平台身份服务 SandIAM 签发的令牌 + 租户号（边界句，SandIAM 本身是插件，其账号与产品侧细节归它自己的文档，本稿不写）。两套身份源互不信任对方的令牌，拿错身份调接口一律拒绝。
- **审计三元组**：插件产生的审计/日志事件统一带「身份来源 + 账号号 + 租户号」（宿主来源租户号恒 `'default'`），落库归内核账本。插件**不另起第二套审计/日志账本**，业务事件可订阅内核事件出口。
- 插件**不自己构造 RequestContext**，身份一律经宿主身份提供方/会话上下文取。
- 鉴权缓存命名空间对插件只读不可写：插件拿到的缓存句柄不能写鉴权命名空间。
- 权限声明机制与宿主同一套：权限点以插件 OpenAPI 片段的 `x-permission` 扩展字段为准，注解 `#[Permission('sand_foo:record:read')]`（已定，总监 11-17）作代码侧标注；**权限点、路由、MCP 工具表构建期统一收集生成注册表，不在运行期反射/注解扫描**（M-12），启动期只做一致性校验；显示名与菜单分组归菜单扩展点声明，不进注解。
- **契约四类声明统一收集 + 契约测试（对照 15/S-05）**：插件包里以 OpenAPI 片段声明接口，宿主构建期统一收集各插件的 OpenAPI 片段、MCP 工具声明、权限点、错误码四类声明并查冲突——路由路径、权限码、错误码、工具名撞名直接构建失败；装/升插件后必跑宿主随内核提供的 `kernel_api` 契约测试套件（扩展点声明完整、权限码形状、错误码在 `x-error-codes` 域内、迁移随包声明），不过拒绝启用。
- 租户上下文归属（M-06）【老板 2026-11-17 已定 R-7】：产品侧租户号由 SandIAM SDK 实现框架的 `TenantContextProviderInterface` 注入，框架中间件校验后写 `RequestContext`；**插件不能自造租户上下文**——各插件各写一套等于绕过统一隔离。
- 授权不越级对插件同样生效：插件页面/接口里涉及角色权限变更、导出等动作，遵守内核高危清单与 sudo 再验证口径；**插件的启用、停用、卸载、删除本身就在 sudo 高危清单里**。
- 日志与留存约定对插件同样生效：敏感字段走统一脱敏器；插件日志结构化、带 `request_id`；不记口令、密钥、令牌、Cookie。

## 7. 数据访问

- 长期形态：插件经**插件 SDK** 拿 DBAL 通道，走宿主同一套纪律——参数绑定、字段白名单、不 `SELECT *`、不裸写 `new PDO`/连接对象/手写 SQL 拼接、方言字面量只许出现在框架方言层文件。
- 过渡期：存量插件可暂用 think-orm，连接配置与宿主同源、读写分离同一套规则；新写代码按 DBAL 通道方向来。
- **读写分离规则覆盖插件**：写后读主（请求内写标记 + 会话最近写入窗口内读主）、事务内全走主、授权判定一律读主。
- **插件库账号**：独立库账号（PG 独立 schema/角色、MySQL 独立账号），按本插件表前缀授权；`sand_system_*` **默认不授权**。插件要用的宿主数据经插件 SDK 提供。说明：独立账号是防 bug 的纵深防御，挡不住同进程恶意插件拿环境配置——信任边界仍是签名 + 代码审查。
- 插件要读宿主侧数据（用户、文件、字典等）一律经插件 SDK 的接口，不直查宿主表。

## 8. 生命周期

状态记账在 `sand_system_plugin` 表（不再用 `info.ini` 当账本）。下载、校验、暂存、已装运行、升级、清理、卸载是不同状态。

- **安装**：先验签后解包（顺序不能反）→ 安装闸（kernel_api 区间、`databases`、依赖审计，见 packaging.md）→ 迁移执行 → 扩展点注册 → 中间件链守卫断言。
- **启用/停用**：生产环境对插件仅有的两个动作；停用前检查、用户交接走扩展点契约。
- **升级**：必须从真实旧版本迁移到目标版本；同版本空迁移不算升级证据。
- **卸载**：插件数据处理三选——**保留（默认）/ 导出后删除 / 直接删除**；卸载流程显式选择、由内核执行；不静默删业务表与数据。
- **异常态**：库里有注册记录但无运行时目录 = `installation-files-missing`，走插件管理的有界清理/恢复路径；不得叫"已安装"，不得静默覆盖。
- **守卫重跑**：插件安装、升级、重新发布完成后必须重跑中间件链守卫（断言无旧鉴权中间件残留、受保护路由有效），断言结果写审计。
- **生效模型**：安装动作与代码生效分离——不做"装了立刻跑任意代码"的热重载，经重启/发布流程生效。

### 8.1 迁移纪律（插件侧）

- 插件迁移 = 包内 `migrations/` 目录的声明式文件序列 + 清单声明；由内核执行器统一收集、统一执行，账本记 `sand_system_schema_migration`、按插件命名空间记账；**账本按连接记**（M-05）——插件用独立命名连接（独立库）时，它的迁移账记在自己连接的库里、迁移锁按连接加。插件不自建执行器、不开私有台账表。
- 双库与回退（老板规矩第 3 条）：插件建表/迁移覆盖 PG 与 MySQL 两库，写法用**双库通用写法**——每份迁移优先写方言无关子集；确有方言差异的，同一逻辑写两套方言由迁移层按目标库分流执行。「每份变更物理交 `.pgsql` + `.mysql` 两个文件」的旧说法作废。**每份迁移必须带回退脚本**，合并前在测试库跑「升级→回退→再升级」；删列删表这类丢数据的步骤，回退脚本里写明「不可逆，靠升级前备份」。回退脚本同一形态。文件命名与宿主迁移规范同一套（与 `sandadmin1x-backend` 的迁移约定一致）。
- **生产环境不执行回退脚本**（M-07）：生产回退 = 切回上一版制品 + 按需恢复备份，本版「先加」类迁移保留不回退；回退脚本只用于测试库验证与「刚上线未写数据」窗口的人工确认应急回退（sudo + 审计）。迁移前执行器先做恢复点检查（`RecoveryPointProviderInterface`：小库现场 dump、大库登记快照号/PITR 位点），拿不到可用恢复点拒绝迁移（M-13）。
- 每份迁移最多一条结构变更；执行只走 CLI，不开 HTTP。
- **执行前逐条静态检查**：只允许操作本插件命名空间前缀的表；出现 `sand_system_*`、`GRANT`、`CREATE FUNCTION`、`COPY ... PROGRAM`、`LOAD DATA` 一律拒绝。
- 破坏性变更按 expand/contract 拆「先加 → 回填 → 换读 → 后删」跨版本走、后删类晚一个版本执行；文件头声明目标版本和 `compatible` 或 `breaking`（已定，总监 11-17）；升级和回退都要可重入。

## 9. 前端接入

- **构建期集成**：插件仓内保留 `web/` 前端源目录（React 19 + Semi Design，与宿主同栈），发行 zip 携带；宿主 `web/` 构建期按 manifest `frontend` 字段收集各插件前端模块、合并编译。
- 包内前端结构（草案）：`plugin-web/<app>/{pages,components,api,routes.ts}`。
- 路由与菜单：走扩展点声明，构建期生成路由表；不许 SQL 插行。
- 插件前端**不能自带第二套 UI 组件库/样式体系**（统一 Semi + Tailwind）；前端依赖只用宿主白名单共享依赖。
- 插件页面**不能直调内核高危接口**，**不能自己弹 sudo 输入框**转嫁再验证——sudo 交互由内核统一出。

## 10. 框架给插件的能力边界（框架保证什么）

- **内核 API**：对外声明语义化版本号；先标 deprecated、过明确弃用窗口才 remove，窗口期写进契约。
- **插件 SDK**：DBAL 连接通道、宿主数据读取接口、事件订阅入口、身份提供方。SDK 来源：由宿主内核随版本提供（宿主仓内契约包/随内核制品分发，插件开发期作 dev 依赖引用），不发独立公共 Composer 基础包（已定，总监 11-17）。
- **扩展点体系**：第 4 节列出的扩展位与公开契约文档。
- **迁移执行器 + 统一账本**：插件按命名空间记账，不自带。
- **审计落库**：插件事件经内核账本记「身份来源 + 账号号 + 租户号」三元组。
- **安全响应头**：插件页面纳入统一安全响应头与 CSP。
- **定时任务执行**：清单声明的 handler 由内核调度执行，参数过 schema 校验。
- **插件间契约冻结**：把 UI/对接面交给他人开发前，先冻结路由、DTO 字段、权限、错误、字段字典并写下来。

## 11. 插件禁止清单（逐条可查）

1. 不直写 `sand_system_*` 内核表（含菜单/授权插行）。
2. 不自带登录、权限、用户体系；不另开鉴权链；不挂 `CheckLogin`/`CheckAuth` 类旧中间件。
3. 不自己构造 `RequestContext`；不绕开宿主身份提供方取身份。
4. 不自带安装器、更新器、网页终端。
5. 不经网页上传 zip 获得代码执行；不提供"装了立刻跑任意代码"的热重载。
6. 不另起第二套审计/日志账本。
7. 不依赖旧兼容层（sand-core）的基类/中间件/缓存/模型：`BaseController`、`BaseModel`、`BaseLogic`、`BaseValidate`、`CheckLogin`、`CheckAuth`、`SystemLog`、`service\Permission` 注解、`ApiException`、`UserAuthCache`、`UserInfoCache`、宿主 `SystemUser` 等模型、`exception\Handler`。
8. 不自建迁移执行器、不开私有迁移台账。
9. 迁移文件不写 `sand_system_*`、`GRANT`、`CREATE FUNCTION`、`COPY ... PROGRAM`、`LOAD DATA`——出现即拒绝执行。
10. 包内不带 `vendor/`、`node_modules/`；不私用未白名单的前端依赖。
11. 不绕过扩展点做隐式接入（SQL 插行、扫目录注册）。
12. 不留默认路由面：`disableDefaultRoute()` 空操作不算数，必须逐控制器禁用、逐条声明路由。
13. 不写鉴权缓存命名空间。
14. 不让插件页面直调内核高危接口、不自弹 sudo 框转嫁再验证。
15. 不绕过框架权限与审计：权限判定只认 v1 权限码，审计事件只进内核账本，不留旁路。
16. 不自造租户上下文：租户号只能经框架 `TenantContextProviderInterface` 注入 `RequestContext`（M-06【老板 2026-11-17 已定 R-7】）。
17. 不把租户数据类工具挂框架 MCP（M-04）；不让插件身份直执高危档 MCP 工具——高危写只生成待确认请求（M-02）。
18. 不在运行期反射/扫描注册权限点、路由、MCP 工具——四类声明构建期统一收集（M-12/对照 15）。
19. TypePHP 硬规矩同样生效：`declare(strict_types=1)`、全量类型标注、不用魔术方法（`__get`/`__call` 等）/动态属性/动态调用/变量变量、常驻进程不放请求级全局状态。

## 12. 测试与门禁（AI 闭环对插件同样生效）

- 插件必须带测试；只在分支改，走 PR 与门禁（静态检查 + 编译/构建检查 + 测试全过）才合并。
- 插件仓供应链门禁与宿主同款：lockfile 入库、CI 依赖审计、SBOM 随包、第三方代码登记。
- 接口契约（OpenAPI/约定文档）是权威；跨插件契约冻结后才能交他人开发。
- 插件不依赖框架里不存在的扩展点：用到的内核 API 必须在 `kernel_api_min`/`kernel_api_max` 声明区间内真实存在。
