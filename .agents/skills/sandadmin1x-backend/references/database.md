# 数据库：双库写法、编号、迁移

适用范围：SandAdmin 1.x 宿主与宿主侧所有建表、改表、迁移、查询代码。服务端数据库 = **PostgreSQL 15+ 和 MySQL 8.0+**（老板原话下限，原「8.0.16+」写法作废；推荐并测试 8.4 LTS；各特性所需小版本与退路见 v4 L-1——MySQL CHECK 约束 8.0.16 起才生效，低于它被静默忽略、由应用层校验兜底）。双库是对代码的要求，不构成对单个插件部署目标的强制——插件可经 manifest `databases` 声明单库例外（如 SandAI 仅 PG），装错库由安装闸拦截。自营生产部署选 PG 是技术总监技术选型，不限制私有部署用 MySQL。SQLite 不进服务端。

## 一、数据访问只有一套

- 唯一入口：Doctrine DBAL + 自研仓储方言层（`server/src/Infra/Db`），抽象 `Repository<T>` + 字段白名单 + 参数绑定。
- 业务代码**禁止**：裸写 `new PDO`/`DriverManager::getConnection`、手写 SQL 拼接、`SELECT *`、读写 `fieldMap` 白名单之外的字段。
- 方言层只放四件事：大小写不敏感搜索、upsert、JSON 查询、咨询锁。**除此之外的方言差异不许存在**。
- `ON CONFLICT`/`ON DUPLICATE KEY`/`FOR UPDATE`/`SKIP LOCKED` 等方言字面量**只允许**出现在 `src/Infra/` 方言文件里（NoDialectSqlRule 静态检查会拦）。
- 新代码禁用 think-orm/Eloquent（它们随旧面退役）；授权判定类查询（数据范围、部门归属、对象归属、安全设置、权限版本）一律 `forAuthz()` 读主库。
- 事务：写操作包事务，锁内只做读核+写——密码校验、验证码图生成、坐标比对等重活**禁止**放锁/事务里；死锁按有限重试（≤3 次）处理，不无限重。
- MySQL 并发坑必须知道：`INSERT ... ON DUPLICATE KEY UPDATE` 有已知死锁面、RR 等值未命中锁间隙；规避顺序：短事务 → 先 UPDATE 后 INSERT → 必要时 READ COMMITTED → 有限重试。

## 二、表结构硬规矩

命名（详见仓库《命名与注释规范》，这里列最常用的）：

- 表名 `sand_<模块>_<单数名词>`，去掉前缀后 ≤3 词 ≤30 字符；列名小写 snake_case ≤30 字符，不以本表名词开头。
- 主键一律叫 `id`；外键 `<对方名词>_id`；操作人 `created_by`/`updated_by`/`requested_by`。
- 时间字段一律 `datetime`、后缀 `_time`：审计三件套 `create_time`/`update_time`/`delete_time`（软删，NULL=未删）；**禁止** `*_at` 后缀命名和 int 时间戳。
- 布尔：`is_/has_/can_/must_` 开头或形容词，两库都用 `boolean`（MySQL 落 `tinyint(1)` 等价、只用 0/1），**禁止** 1=是/2=否 的旧 `sa_*` 口径（加 `CHECK (col IN (0,1))` 锁取值——8.0.16 以下静默忽略、由应用层校验兜底；已定，总监 11-17）。
- 状态：启停用 `status`（1 启用 2 停用）；流转用 `state`（字符串，取值用 CHECK 约束列出）。`status` 只在启停有业务语义时加，不对审计/事件等不可变记录机械加。
- 索引/约束前缀：`uk_`（唯一）`ix_`（普通）`fk_`（外键）`ck_`（检查）+ 完整表名 + 列名，全名 ≤63 字节。
- 两库都支持 COMMENT 的列一律写 COMMENT。
- 可编辑的配置/业务表加 `version` 乐观锁列：更新带版本条件、冲突返契约错误码 409（S-03）。
- 分区表在 PG/MySQL **两个库上一律不建数据库级外键**（M-14：MySQL 分区表不支持外键——不能当父表也不能当子表；PG 虽允许但为双库写法一致统一不建）；引用完整性靠应用层校验 + 定期对账任务（孤儿行巡检归任务调度）。
- `sand_system_*` 是内核表，归内核独占；插件表用插件自己的前缀，不许碰 `sand_system_*`。
- 宿主表**一律不加** `org_id`/租户/组织列——1.x 框架本身单租户，多租户是将来独立版本的事（T-1）。`OrgContext`/`ShardResolver`/`ConnectionResolver` 三接口是留给将来多租户版本的约定，单租户恒返回固定值——业务代码不自己拼"属于谁"的条件、统一走仓储入口，不当多租户能力用（已定，总监 11-17）。
- 软删：审计三件套 `delete_time` 已在；1.0 只做软删查询作用域，回收站页 1.1 再做。
- 附件/图片字段：**统一存文件记录 id**（JSON 数组或关联表），不存 URL 串——1.x 文件走统一存储驱动，下载地址可能是签名临时地址，对外链接走文件记录的 nanoid 列（已定，总监 11-17）。
- 词表：`task` = 后台任务、`schedule` = 定时任务；`sand_system_task_run` 是任务运行记录表（雪花主键），两个概念不混用。

## 三、编号规则（老板定，两类）

| 场景 | 主键 | 说明 |
| --- | --- | --- |
| 数量可预见的表：账号、部门、岗位、菜单、角色、字典、设置等 | `int` 自增 | PG 写 `int GENERATED BY DEFAULT AS IDENTITY`，MySQL 写 `int unsigned AUTO_INCREMENT` |
| 不可预见持续增长的表：日志、会话、票据、任务运行记录等 | 雪花 64 位 `bigint` | 应用层发号（v4 J-3 方案甲），写入时赋值，不靠数据库 |

- 雪花位布局：**41 位毫秒 + 13 位节点 + 9 位序列**，纪元 2026-01-01；节点号按部署分段、由配置分配，启动自检不在本部署号段内拒绝启动；节点登记表 `sand_system_id_node` 归可预见类 int 自增（记录各部署节点号分配）。
- **接口里 id 一律输出字符串**——64 位整数会丢 JavaScript 精度；`openapi.yaml` 里雪花 id 字段就是 string。
- 外键与被指向主键同型：指向雪花表的外键 `bigint`，指向 int 表的外键 `int`。
- **nanoid 只用于对外不可猜的链接**（文件下载、分享等），单独一列、不当主键。
- 全局唯一编号**不得无差别使用**：能用 int 自增说清楚的就自增。
- 节点号段按部署配置 `idgen.node_range` 声明、**不写产品名**（S-16）；节点号从 `sand_system_id_node` 租用（数据库租约，不依赖 Redis）或在配置 `idgen.node_id` 写死。
- 逐表归类以《编号两列表-修订》（`audit-idlist-1117/编号两列表-修订.md`）为准——**该清单在老板审表前是草稿**，写表时按它归类、遇到未登记的表先归类再登记，不擅自发明第三类。现行框架口径：自增 28 张、雪花 19 张、共 47 张。几个容易归错的：`sand_system_user`、`sand_system_role`、`sand_system_dept`、`sand_system_api_token`（机器令牌，v2 返工后归自增）归可预见类 int 自增；`sand_system_session`、`sand_system_login_log`、`sand_system_audit_log`、`sand_system_recovery_ticket`、`sand_system_task_run`、`sand_system_outbox`、`sand_system_upload_task`/`sand_system_upload_chunk` 归雪花类 bigint。已删/合并的旧写法不再出现：`sand_system_login_identifier` 已删（宿主量级小直接查账号表）；`sand_system_menu`、`sand_system_role_menu` 已删（菜单写在程序和插件清单里，可改部分存 `sand_system_menu_override`/`sand_system_menu_custom`）；验证码、登录失败计数并入 `sand_system_cache`（临时数据，平时放 Redis）。

雪花表在 PHP 侧这样发号：

```php
public function insert(array $data): string
{
    $data['id'] = $data['id'] ?? $this->idGen->next(); // 应用层雪花，bigint
    $this->repository()->insert($data);
    return (string) $data['id']; // 接口输出字符串
}
```

## 四、双库写法清单

写 SQL/DDL 时按"两库通用子集"思考，写不通用就交给方言层，或在迁移里同一逻辑写两套方言由迁移层分流：

| 需求 | PG 写法 | MySQL 写法 | 通用做法 |
| --- | --- | --- | --- |
| int 自增主键 | `GENERATED BY DEFAULT AS IDENTITY` | `AUTO_INCREMENT` | 迁移层按目标库输出 |
| upsert | `ON CONFLICT` | `ON DUPLICATE KEY UPDATE` | 只走方言层封装，业务不碰字面量 |
| JSON 列 | `jsonb` + 索引 | `json` + 生成列索引 | 查询走方言层 |
| 取回插入行 | `RETURNING` | 不支持 | 写后按唯一键回读 |
| 时间精度 | `timestamptz` | `datetime(6)` 存 UTC | 应用层统一 UTC |
| 咨询锁 | `pg_advisory_lock` | `GET_LOCK` | 只走方言层 |
| CHECK 约束 | 原生 | 8.0.16+ 生效 | 照写 + 应用层兜底校验 |

- 每写一条带方言味的东西先问自己："这一条 MySQL 能不能原样跑？"不能就进方言层或写两套方言。
- 序列、存储过程、触发器、物化视图这类单库特性：**新表一律不用**，避开。
- **增长表游标分页（S-02）**：日志/审计/任务运行等按月分区的增长表，列表统一走游标分页（`WHERE id < :cursor ORDER BY id DESC LIMIT n`，雪花 id 天然时间有序），不跑 `COUNT(*)` 全量总数——「总数」按约数口径展示或不展示；深 `OFFSET` 分页禁用（方言层检查）。
- **安全相关 SQL 双库各跑一遍契约测试**（鉴权、权限判定、票据、限流计数，随双库 CI 矩阵：PG 最新 LTS × MySQL 8.0 系末版 + MySQL 8.4 LTS），一库通过不算过；MySQL 侧默认关模拟预处理走原生预处理，`likeEscape` 只走方言层封装。
- 审计/日志/搜索写入不裸写表：安全类日志统一走 `AuditSinkInterface`（默认库表 + 异步批量写，可换列式库/搜索引擎/对象存储 WORM；防篡改哈希链定在接口层），检索走 `SearchInterface`（默认查库表）；MCP 日志检索与后台日志页共用同一查询入口，不直接拼 SQL（M-08）。
- MySQL 8.0 系列已停官方支持（最后版本 8.0.46）：安装/升级自检检出 8.0.x 给明显警告「建议升级 8.4 LTS」并写安装审计，不拦安装（下限仍是 8.0+，R-4）。

## 五、迁移规矩

文件形态（每份迁移覆盖两库）：

- 优先写**方言无关子集**——一份写法两个库都能跑；
- 确有方言差异的，同一逻辑写两套方言，由迁移层按目标库分流执行；
- 回退脚本同一形态、同一规则。

纪律（必须逐条照做）：

- 命名 `<4位序号>_<动词>_<对象>`，序号连续不跳号；文件头声明目标版本和 `compatible` 或 `breaking`（已定，总监 11-17）。
- **每份最多一条结构变更**；破坏性变更按 expand/contract 拆"先加 → 回填 → 换读 → 后删"跨版本走，「后删」类**晚一个版本**执行。
- 每份迁移**必须带回退脚本**：回退脚本做升级脚本的逆操作，保证按序号倒序执行能回到上一个结构版本；合并前在测试库跑"升级 → 回退 → 再升级"。存量历史迁移压成一份基线迁移（S-07）——基线本身不要求 down，基线之后的新迁移强制带 down。
- **生产环境不执行回退脚本**（M-07）：生产回退默认只切回上一版制品，本版「先加」类迁移保留不回退；回退脚本只用于两处——合并前测试库验证，以及「刚上线、还没写入新数据」的极短窗口内经人工确认（sudo + 审计）的应急回退；已写入数据的丢数据变更一律靠备份恢复。
- 删列、删表等丢数据的变更，回退脚本里写明"**不可逆，靠升级前备份**"；升级前必须备份，拿不到可用备份拒绝升级。
- 升级和回退都要**可重入**：重复执行不报错不重复建（`IF NOT EXISTS`/先查再动）。
- 执行只走 CLI（`bin/sand migrate` 一类），**禁止** HTTP/网页执行迁移；宿主和插件迁移共用一套执行器，账本按连接记（M-05）：每条数据库连接一本同结构账本 `sand_system_schema_migration`，按命名空间区分归属，迁移锁按连接加——插件用独立命名连接时，它那本账记在自己连接的库里。
- 执行器带迁移锁；检测到半成品库（账本校验对不上）拒绝继续。
- 迁移前先确认有可恢复点（M-13，`RecoveryPointProviderInterface`）：小库/单机允许执行器现场 `pg_dump`/`mysqldump`；大库不做全量导出，人工登记快照号/PITR 位点经 `--recovery-point` 传入并写审计。**没有恢复点实现时拒绝迁移，不静默跳过**——回退脚本管"结构回滚"，备份管"数据兜底"，两者不互相替代。
- **已发布的迁移不改名、不改内容**；要改结构就出新迁移。
- 不写插件包内自执行 `install.sql`/`update.sql`/`uninstall.sql`；插件结构变更也是迁移文件序列，交内核执行器（细节归 plugin skill）。

## 六、表与账号权限

- 数据库账号最小权限分五类：运行账号（业务 DML，**对审计/登录日志表只有 INSERT+SELECT**）、迁移账号（有 DDL 只给 CLI）、日志清理账号、只读账号、插件账号（按表前缀授权，`sand_system_*` 默认不授权）。web 进程账号启动自检无 DDL 权限。
- `sand_system_audit_log`、`sand_system_login_log` 界面和 API **没有**删改入口；清理由独立账号按留存期删过期行。
- 跨主机传输默认强制 TLS（PG `sslmode=verify-full`、MySQL `MYSQL_ATTR_SSL_VERIFY_SERVER_CERT`），不满足拒启，除非显式 `allow_insecure_db_transport=true`。

## 七、建表示例（同一逻辑两套方言，由迁移层分流）

```sql
-- 0007_add_dept（PG 方言）
CREATE TABLE sand_system_dept (
  id           int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  parent_id    int          NOT NULL DEFAULT 0,
  name         varchar(50)  NOT NULL,
  leader_id    int,
  status       smallint     NOT NULL DEFAULT 1,
  sort_num     int          NOT NULL DEFAULT 0,
  created_by   int,
  updated_by   int,
  create_time  timestamp    NOT NULL DEFAULT now(),
  update_time  timestamp,
  delete_time  timestamp,
  CONSTRAINT ck_sand_system_dept_status CHECK (status IN (1, 2))
);
CREATE INDEX ix_sand_system_dept_parent ON sand_system_dept (parent_id);
COMMENT ON TABLE sand_system_dept IS '部门';
```

```sql
-- 0007_add_dept（MySQL 方言）
CREATE TABLE sand_system_dept (
  id           int unsigned   NOT NULL AUTO_INCREMENT PRIMARY KEY,
  parent_id    int unsigned   NOT NULL DEFAULT 0,
  name         varchar(50)    NOT NULL,
  leader_id    int unsigned,
  status       tinyint        NOT NULL DEFAULT 1,
  sort_num     int            NOT NULL DEFAULT 0,
  created_by   int unsigned,
  updated_by   int unsigned,
  create_time  datetime       NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time  datetime       NULL,
  delete_time  datetime       NULL,
  CONSTRAINT ck_sand_system_dept_status CHECK (status IN (1, 2)),
  KEY ix_sand_system_dept_parent (parent_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='部门';
```

持续增长表的主键换成 `id bigint NOT NULL PRIMARY KEY`（两库同写法，应用层雪花发号、接口输出字符串），不再有自增子句。
