# SandAdmin 1.x 设计高标准清单

本 skill 是 1.x 所有设计与方案的**底线考卷**。老板 2026-11-19 原话：「设计先按高标准、规格来，再根据实际情况做减法，不能一上来就给低水平产品。」另一句：「做一个安全、稳定、高效的框架，我以为高效能涵盖了高性能」——所以「高性能」单列成组（P 组），每组数字必须有来源。

## 用法（审计硬规则）

1. 任何设计/方案/架构稿（含插件方案）必须**逐项回答**本清单 54 条：每个编号给出「本方案怎么做」或「不涉及 + 理由」。空着不算不涉及。
2. **先按高标准写，再做减法**：每个编号先答「高标准要求」那一格的水平；做不到或版本里不做的，减法必须写两栏——「理由」和「以后补的代价」。只写"不做"不写代价的，审计一律打回。
3. 数字一律带来源：公开基准（URL + 轮次 + 测试类型 + 硬件）、官方文档，或明确标「须 1.0 压测定基线」。凭感觉写数字一律打回。
4. PHP 主流 FPM 框架（Laravel / ThinkPHP FPM 模式）只当**底线**，不当目标；目标对标 Go（Gin、go-zero、Kratos）和 Java（Spring Boot、Spring Cloud、Vert.x、Quarkus）一流框架，对标表见末节。
5. 「1.0 做什么 / 1.1 做或不做」两列是本仓当前基线答案：设计与基线一致可直接引用编号；要改基线的，在方案里写偏差理由，审计连同理由一起核。

## 规模口径（老板已定事项总表第 8 条，2026-11-15【定论】原文）

> 「规模：律序用户量要算执业律师、实习律师、助理、律所员工及未来当事人端，几百万是保守数；sandadmin 1.x 不以律序为上限，要能平滑扩展到几千万、上亿用户（基础层留好扩展接口，第一版不必全做满）。」

落到设计的翻译：第一版不必全做满，但**每个编号都要回答"到几千万、上亿时怎么扩"**——留接口不留债。「第一版没做」和「没留接口以后做不了」是两回事，前者可接受，后者打回。

## 清单主体（54 条；编号与名称已定稿，不得增改删；追加条目只许加在末尾并标「追加」）

列含义：高标准要求 = 对标一流框架应到的水平（一句话）｜1.0 做什么 = 首期版本落地的下限｜1.1 做或不做 = 下一版计划｜理由 = 为什么这样排｜以后补的代价 = 现在欠的以后要花多少补｜验收指标 = 可量化、可测的判据。引用 v4 = 《顶层架构设计-v4》（review-1117-r3）同口径。

### D 数据层

| 编号 | 条目 | 高标准要求 | 1.0 做什么 | 1.1 做或不做 | 理由 | 以后补的代价 | 验收指标 |
|---|---|---|---|---|---|---|---|
| D1 | 主从与读写分离 | 读写自动分流，从库可挂多台，主从延迟可观测 | 做：DBAL 层主从路由（老板已定 B-2），读默认走从库、写和显式一致读走主 | 不做：按权重/延迟自动选从库 | 首期 300 请求/秒一主一从足够（v4 I-2） | 加从库选择策略只改 DBAL 路由层，业务代码零改 | 压测中读流量落从库可证；停从库自动回主并有告警 |
| D2 | 连接池 | 有界连接预算、启动自检、超预算拒绝启动、峰值 ≤70% | 做：每进程预算（宿主主从各 1 + think-orm 各 1，命名连接另计），max_connections ≥ 预算 1.5 倍且 ≥200，生产进程数按压测写死（v4 P 节连接账） | 不做：进程间动态借调 | PHP 同步驱动每连接一进程用，池化语义就是预算制 | 装新插件重算连接账是评审动作不是改造；真做池化要换异步驱动，大改 | 启动自检脚本输出预算账；压测峰值连接 ≤max_connections 70% |
| D3 | 分库分区 | 分片路由层可插拔、按租户分库路径明确 | 不做实现，做接口：租户路由层接口预留，大表按分区设计（MySQL 分区表不建外键，v4 L 节） | 不做 | 首期 1.5 万用户单库足够；分库属千万级升档项（v4 I-5） | 已留接口则升档 = 路由层实现 + 搬迁工具；不留接口等于推翻表结构，不可接受 | 接口定义进契约清单；扩展路径文档逐档列「加什么、改不改业务代码」 |
| D4 | 全局编号 | 编号策略统一、防猜、JS 精度安全、发号不撞 | 做：雪花 64 位 bigint（41 位毫秒 + 13 位节点 + 9 位序列，应用层发号，接口输出字符串）；可预见表 int 自增；nanoid 单列不作主键（老板 11-17 改定） | 不做：集中发号服务 | 应用层发号单机够用，节点位已按约 2,000 进程重排（v4 J-3） | 节点位不够要重排位布局，落库后难改——所以 1.0 就必须按千万级进程数排好 | 全表按可预见/不可预见两列归类清单；并发发号压测无重复 |
| D5 | 事务一致性 | 本地事务默认正确；跨连接/跨服务用 outbox 保证最终一致 | 做：DBAL 事务 + outbox 表随业务库走、relay 按连接登记、message id 去重（v4 插件命名连接四规则） | 不做：saga/分布式事务协调器 | 首期无跨服务写场景，outbox 已覆盖插件异步落账 | 上 saga 要引入协调器和补偿表，中改；outbox 账本结构不变 | ≥2 实例门禁：outbox 不重复外发；强杀 mid-flight 后重放不丢不重 |
| D6 | 慢查询治理 | 慢查询有阈值、有记录、有处置通道；大表变更不走裸 DDL | 做：PG `statement_timeout` 5 秒 / MySQL `max_execution_time`、迁移 `lock_timeout` 5 秒；大表（>100 万行或 >10 GB）走在线变更通道，限速可暂停（v4） | 不做：自动 explain 巡检报告 | 阈值和通道先于自动化，自动化没有人工处理通道也是摆设 | 补自动巡检 = 加一个任务读慢日志，小改 | 压测无超时请求堆积；慢查询表可按端点聚合查询 |

### H 高可用

| 编号 | 条目 | 高标准要求 | 1.0 做什么 | 1.1 做或不做 | 理由 | 以后补的代价 | 验收指标 |
|---|---|---|---|---|---|---|---|
| H1 | 多实例无状态 | 任意实例可服务任意请求，请求状态不留进程 | 做：平台 ≥2 实例实测门禁四件事（会话跨实例、定时任务不重复跑、outbox 不重发、滚动升级不丢请求，v4） | 不做：自动弹性伸缩 | 无状态是平滑扩容和 reload 的共同前提 | 补在 H3/P4 脚本层，代码零改 | 四件事在研发环境实测通过即算 1.0 达标（v4 R-5 口径） |
| H2 | 会话共享 | 会话存共享存储，单实例故障不踢人 | 做：默认 Redis 会话 + 六条件门禁（跨可用区主备、AOF everysec、noeviction 独立实例、Redis 挂返回 503+Retry-After 不返 401、运行中不自动切库、停主演练，v4 J-6） | 不做：会话多写双存储 | 六条件已把单 Redis 的风险压实；双写一致性收益抵不过复杂度 | 换驱动是计划内变更需全员重登，写进客户端约定即可 | 压测中停 Redis 主：只出 503 不出 401、5xx 持续 ≤60 秒、恢复后不用重登 |
| H3 | 故障切换 | 依赖故障有切换路径，自身多实例互为备份 | 做：主库主备 + Redis 主备切换演练；双可用区部署文档；每套 SandIAM ≥2 实例 | 不做：跨地域应用多活（容灾归 M2） | 首期单地域，跨地域是 I-1 高档位项 | 多活=数据层单元化先行，在 D3 接口上叠加，大改但路径已写 | 切换窗口 5xx ≤60 秒；切换后已登录会话不受影响（除 AOF 窗口丢失） |
| H4 | 健康检查 | 存活/就绪分离的标准端点，就绪反映真实依赖 | 做：`/health/live` 与 `/health/ready` 分离（对标 Quarkus `/q/health/live|ready`），ready 检查 DB/Redis 依赖 | 不做：启动探针/细粒度组件探针 | 两个端点已覆盖 LB 与滚动发布所需 | 加探针是增量，无代价 | ready 在 DB 断开后变不健康；live 不受依赖故障影响 |
| H5 | 优雅停机 | 收到停机信号后停收新请求、在途请求限期完成、超时强退 | 做：workerman 平滑重载机制（主进程逐个子进程安全退出再重建）+ 滚动发布先加后删；对标 Spring Boot graceful（默认开、网络层拒新、timeout-per-shutdown-phase） | 不做：停机前排空调用方的 LB 摘除钩子脚本（1.1 补） | workerman 原生能力 + 实例门禁已覆盖单机到多机 | 补 LB 钩子 = 运维脚本，零代码 | 24 小时浸泡中平滑重载零失败（v4 P-4）；在途请求完成率 100% |

### A 异步与并发

本组实现细节以 **3i 异步并发补充设计为准（编制中）**；每栏仍按基线填满，3i 稿出后以其细化口径修订本组。

| 编号 | 条目 | 高标准要求 | 1.0 做什么 | 1.1 做或不做 | 理由 | 以后补的代价 | 验收指标 |
|---|---|---|---|---|---|---|---|
| A1 | 任务队列 | 持久化、ack/重投、并发抢占，集群内同任务不重复跑 | 做：库表抢占单跑的后台任务（v4 J-11），大导入导出超阈值转后台 | 不做：独立消息队列中间件（百万级升档项，v4 I-5） | 首期量库表队列够；独立 MQ 升档再上 | 库表→MQ 只换执行器实现，任务契约不变 | ≥2 实例门禁：限时/周期任务不重复跑 |
| A2 | 重试 | 指数退避 + 抖动 + 最大次数，策略可配 | 做：失败任务按退避策略重投 | 不做：按错误类型分级退避 | 统一退避已覆盖首期场景 | 加分级策略 = 配置扩展，小改 | 任务失败后按策略重投；超上限转死信 |
| A3 | 死信 | 重试耗尽入死信、可查、可人工重放 | 做：死信记录 + 后台重放入口 | 不做：死信自动分析 | 死信不处理等于静默丢任务 | 自动分析锦上添花，无债务 | 构造连续失败任务可见死信且重放成功 |
| A4 | 幂等 | 所有写接口可带幂等键，重复提交不产生重复效果 | 做：MCP 写工具强制幂等键；outbox message id 去重；表级唯一约束兜底 | 不做：全接口自动生成幂等键 | 写接口幂等是对外契约底线，不能省 | 后补 = 补键列和去重表，中改，但现在不做以后要改客户端 | 同键重复提交返回原结果不新建记录 |
| A5 | 分布式定时任务与锁 | 集群内定时任务单跑，锁有超时和 fencing | 做：schedule 库抢占单跑 + Redis 锁（noeviction 实例） | 不做：leader 选举服务 | 库抢占 + Redis 锁覆盖首期规模 | 选主服务属大基础设施，无需要 | 两实例下同一 schedule 不并发执行；锁持有者宕机后锁自动释放 |
| A6 | 容量目标（QPS/在线数/P99） | 目标数字明确、可测、分档位 | 做：v4 I-2 口径——设计 300 请求/秒、压测 750、AI 并发 300 路、高峰在线 2,000；延迟按 I-4 分类型表 | 不做：更高档位的实测承诺（成长档以后按触发条件升） | 数字已定档，混用目标档和首期档是 M1 审计点 | 改档 = 改配置和压测门禁参数，零代码 | P-4 三条压测门禁全过（见 Q1/P1） |
| A7 | 进程或协程模型 | 运行模型写明，进程角色、数量、并发上限可算可配 | 做：常驻多进程、不开协程（v4 运行模型）；进程组角色与挂路数上限由 `ProcessProfileInterface` 声明，插件不直连 workerman 原语 | 不做：协程运行时（Swoole/Fiber 调度） | PHP 协程生态与现有同步库不兼容，引入代价大于收益（v4 ADR-09） | 换协程 = 换运行时 + 全部 IO 库适配，大改；无计划 | 进程数配置写死进配置清单；每进程挂路数上限生效可证 |
| A8 | 背压 | 过载时显式拒绝而非排队到崩，队列有上限 | 做：每进程挂路数上限、限流 429+`Retry-After`、慢模型 30 秒+ 压测时普通请求 P95 不变差（v4） | 不做：自适应负载卸载（如 go-zero SheddingHandler 按 CPU 卸载） | 固定上限背压首期够用；自适应卸载要接入负载信号采集 | 补自适应卸载 = 中间件级改造 + 指标管线，中改 | 300 路 AI + 慢模型压测：普通请求 P95 不变差、超限请求被 429 而非挂死 |

### C 缓存

| 编号 | 条目 | 高标准要求 | 1.0 做什么 | 1.1 做或不做 | 理由 | 以后补的代价 | 验收指标 |
|---|---|---|---|---|---|---|---|
| C1 | 分级 | 进程内/分布式/源分级清晰，各级职责明确 | 做：Redis 为分布式缓存（`allkeys-lru`，与会话 `noeviction` 实例分开），缓存键一律带 TTL；进程内只许放不可变资源 | 不做：本地二级缓存同步 | 首期单机进程数有限，进程内缓存广播收益小 | 补二级缓存 = 订阅失效消息，接口已在 C2 留 | 全部缓存键静态检查有 TTL；会话与缓存不同实例 |
| C2 | 失效 | 变更后及时失效，版本化 key 可广播 | 做：权限/字典等变更走失效广播；默认 TTL 兜底 | 不做：失效事件总线（复用 Redis pub/sub 即可） | 变更频次低，TTL+广播覆盖 | 无实质债务 | 权限变更后下次请求生效，不留旧权限窗口 |
| C3 | 击穿与雪崩防护 | 热点互斥重建、TTL 抖动、穿透防护 | 做：空值短 TTL、TTL 加随机抖动、热点重建加互斥锁 | 不做：布隆过滤器 | 首期数据量用空值缓存够 | 加布隆过滤器 = 前置过滤层，小改 | 压测中清热点键：重建只有一次打到库，雪崩无尖峰 |

### T 流量

| 编号 | 条目 | 高标准要求 | 1.0 做什么 | 1.1 做或不做 | 理由 | 以后补的代价 | 验收指标 |
|---|---|---|---|---|---|---|---|
| T1 | 限流 | 多维（IP/用户/端点）多级限流，共享计数，安全类 fail-closed | 做：Redis 计数全局限流（禁进程内近似），默认阈值表进配置（登录每 IP 每分钟 10 次、每账号每小时 20 次等，v4）；429 + `Retry-After` | 不做：自适应限流（Kratos BBR 式） | 固定阈值压测后可调，先求正确分布 | 自适应算法可换 limiter 实现，接口同构，中改 | 压测超阈值返回 429；两实例共享计数准确；Redis 故障时安全类端点 fail-closed |
| T2 | 熔断降级 | 下游调用按实例熔断，半开探测，降级有兜底 | 部分做：对 SandIAM、AI 上游有超时 + 降级路径（停 SandIAM 演练进 1.0 门禁）；通用下游熔断组件不做 | 做：下游调用统一 wrap + 熔断器（对标 go-zero SRE 公式、Kratos 按 operation 熔断、Resilience4j） | 首期外部依赖少（SandIAM/AI/邮件/对象存储），逐个特判比通用组件更可控 | 依赖越多越难补——外呼点分散后要逐个改；所以 1.0 就要求外呼统一走接口层 | 停 SandIAM 演练：503 不返 401、高危操作连不上 1 分钟即拒；AI 上游超时按超时表执行 |
| T3 | 超时 | 一切外呼必带超时，分层预算不叠加 | 做：PG `statement_timeout` 5 秒、迁移 `lock_timeout` 5 秒、邮件/对象存储连接 5 秒总 30 秒、AI 首字 30 秒硬线（v4） | 不做：自适应超时 | 无超时外呼是事故源头，没得商量 | 补自适应 = 改超时来源，小改 | 慢依赖压测：超时按表生效，无线程/进程堆积 |

| 断线补发 | 断线后按游标补发，稳态查库 ≈0 | v4（改推送算式段） | 断线重连校验补发完整且无重复 |

### P4 发版不停服（平滑重载）

| 项 | 目标值 | 来源 | 测法 |
|---|---|---|---|
| reload 零失败 | 24 小时浸泡中途平滑重载零失败 | v4 P-4 浸泡段（内部口径）；机制：workerman 主进程逐个子进程安全退出重建（manual.workerman.net/doc/zh-cn/faq/reload-principle.html） | 浸泡压测中执行 `php start.php reload`，统计失败请求数 = 0 |
| 长连接进程 | WebSocket/SSE 维持进程 `reloadable=false`，业务进程单独 reload | workerman 官方手册同页「长连接业务 reload 会断连」解法 | 进程配置审查 + reload 演练 |
| 多实例滚动 | 新旧并存期请求不丢、迁移 expand/contract 不报错 | v4 ≥2 实例门禁（对标 Spring Boot graceful：默认开启、在途请求限期完成、网络层拒新——docs.spring.io/spring-boot/reference/web/graceful-shutdown.html） | ≥2 实例滚动发布演练 |

### P5 单进程崩溃自愈

| 项 | 目标值 | 来源 | 测法 |
|---|---|---|---|
| 进程重建 | `kill -9` 后 ≤5 秒恢复服务（**须 1.0 实测定基线**；机制保证：workerman 主进程监控、子进程退出即重建——manual.workerman.net/doc/zh-cn/development/before-development.html） | 官方手册（机制）；目标值为自定，须压测复核 | 压测中随机 kill 业务进程，测恢复耗时并入报告 |
| 内存安全重启 | 进程内存近 `memory_limit` 自动安全重启不影响业务 | webman monitor 进程（webman.workerman.net/doc/zh-cn/others/monitor.html） | 构造内存增长场景验证重启且零请求失败 |
| 连续崩溃 | 同进程短时间内连续崩溃 3 次触发告警 | 自定规则（须 1.0 定基线） | 注入必崩代码验证告警发出 |

### P6 常驻内存安全

| 项 | 目标值 | 来源 | 测法 |
|---|---|---|---|
| 内存平稳 | 24 小时浸泡前后各进程 RSS 增长 ≤10%（基线按压测定稿） | 推导：无公开数字，`max_requests` + 内存水位重启是兜底（v4 卫生规则） | 浸泡段首尾采样各进程 RSS，计算斜率 |
| 状态隔离 | 请求结束断言无遗留请求态，断言失败 = 0 | v4 常驻进程卫生规则（内部口径） | 断言日志审计 + 故意遗留测试用例 |
| 泄漏定位 | 任一进程 RSS 超水位线自动重启且事件入日志 | webman monitor（官方手册） | 构造泄漏场景验证重启记录 |

| workerman 优势 | 落到的清单编号 | 具体能力 | 反面风险 → 对冲编号 |

## 对标一流框架表（六维度）

Laravel/ThinkPHP FPM 只作底线（Benchmarker：laravel 1,741 req/s @c64，约为 webman 的 1.6%）。对标对象是 Go（Gin、go-zero、Kratos）与 Java（Spring Boot、Spring Cloud、Vert.x、Quarkus）。「几成」是工程估算，依据写在每行。

| 维度 | 一流框架怎么做 | webman 上能做到几成（依据） | 做不到的原因 | 以后的补法 |
|---|---|---|---|---|
| 吞吐与延迟 | Gin 111,896 req/s、vertx 199,842、quarkus 151,114、spring 58,750（Benchmarker c64，2026-11-19 抓取，滚动数据集）；TFB R23 Fortunes vertx 1,040,599、quarkus 1,028,408（56 核 + 40Gbps 口径） | **裸 HTTP 与 Gin 持平（约十成：webman 110,952 vs gin 111,896），约为 Quarkus 七成（73%）、Vert.x 五六成（56%）**；workerman 裸 173,597 是去掉框架层的上限——webman 框架层开销约损 36% | 框架层（路由/中间件/请求封装）相对 workerman 裸实现损耗约 36%（110,952 vs 173,597）；再往上是 PHP 同步 IO 模型上限；业务侧瓶颈在 DB 不在框架（官方：带库单查 1–2 万 vs hello 8–16 万） | 追上限靠框架层精简（路由/中间件裁剪）与 TypePHP 编译消运行时开销——效果**须压测验证**；与 Gin 持平已满足「对标 Go 主流」要求，Vert.x 档非 1.x 目标 |
| 连接池 | Go `sql.DB` 池；Java HikariCP 池内复用 | **六七成**：做连接预算 + 启动自检 + 峰值 70% 门禁（v4 连接账公式）；没有池内动态伸缩——PHP 每进程同步持有连接，池化语义不同 | 同步驱动一连接一进程用，无跨请求借还 | 维持预算制 + 监控；远期若上异步驱动再议真池化 |
| 服务治理（限流/熔断/降级） | go-zero：SRE 自适应熔断（K=1.5）+ Shedding 卸载 + 全中间件默认开；Kratos：服务端 BBR 自适应限流 429 + 客户端按 operation 熔断 503；Spring Cloud：Resilience4j 滑窗/半开/TimeLimiter/Retry 全配置化 | **六七成**：T1 限流（共享计数、阈值表）+ T3 超时全做；T2 熔断只对 SandIAM/AI 特判，无通用组件；无自适应卸载 | PHP 生态无现成 Resilience4j 等价物；首期外部依赖少，通用组件投入产出比低 | 1.1 做外呼统一 wrap + 熔断器接口（SRE 公式可直接移植，PHP 实现无难度）；自适应卸载依赖 O2 指标管线先行 |
| 可观测 | Quarkus：`/q/health/live|ready|started` + micrometer-opentelemetry 统一 OTLP；go-zero：Prometheus/Trace 中间件默认开；Kratos：contrib/otel + metadata 传播 | **五六成**：O1 结构化日志 + request_id 强、X2 审计哈希链是加分项；O2 基础指标有、Prometheus 生态未接；O3 OTel 未接（注入点已留） | OTel PHP SDK 接入排期在 1.1；非单体内链路首期需求弱 | 1.1 接 OTel SDK + metrics exporter；x-request-id 传播语义参照 Kratos `x-md-global-*` 前缀规则 |
| 优雅停机与不停服发版 | Spring Boot graceful 默认开、在途请求限期完成、网络层拒新（`timeout-per-shutdown-phase`）；K8s 滚动=先加后删 | **八九成**：workerman reload 逐进程重建原生具备 + 浸泡门禁零失败 + ≥2 实例滚动门禁；缺口在长连接分组与 LB 摘除钩子 | 长连接进程需 `reloadable=false` 特判（官方手册明示）；LB 钩子属部署脚本未写 | P4 分组已列入 1.0；1.1 补发布编排脚本（摘除→排干→升级→回挂） |
| 配置管理 | Spring Cloud Config / Nacos / Apollo：中心化 + 版本化 + 监听热更；Kratos config 多源 + watch；go-zero 配置即代码 | **五六成**：分环境 `.env` + 库内开关 + 限流阈值热更做；无中心化、无版本化、无监听推送 | 首期单部署单体，配置中心投入产出低 | `ConfigProviderInterface` 接口进契约清单（G1），实现后置；热更键清单化防止「什么都热更」失控 |
