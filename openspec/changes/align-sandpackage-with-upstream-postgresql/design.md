## Context

动机见 proposal.md。本地对照基线为 `server/vendor/saithink/saipackage/src/plugin/saipackage/`；composer.lock 固定 6.0.2 / `82043f83df45a6186ea872eef3bce388e0ad87e2`。本轮未联网确认最新版本，也未声称上游已覆盖所有运行场景。

观察到上游 InstallLogic 使用 Server、Version、Filesystem、Depends；install 按 SQL、依赖检查、文件部署、依赖更新、清缓存、重启顺序执行。Server::importSql 按行末分号分段，不识别 PostgreSQL dollar-quoted 函数体。现有 PostgresLifecycleSqlExecutor 已提供词法拆分及事务执行，可作为待验证的适配候选。

当前分支 `codex/sandadmin-rename` 已有未提交的恢复逻辑、路由、测试及文档改动。本次规划不覆盖它们。行数来自当前工作树，只说明扩展规模，不作为缺陷或验收指标。

## Goals / Non-Goals

**Goals:** 安装主流程可逐段对应锁定上游；数据库差异集中、可测试；常规包不需要额外恢复协议；现有实例有明确切换边界。

**Non-Goals:** 不新增安装框架、通用工作流或恢复状态机；不修 SandIAM 业务逻辑；不在本次引入完整前端自动构建平台；不自动转换 MySQL 插件 SQL；不宣称数据库事务能回滚文件、依赖或进程操作。

## Decisions

### 1. 采用可对照的上游派生实现

上游 InstallLogic 直接静态调用 Server::importSql，单纯继承并不能替换数据库执行点。以锁定源文件恢复本地派生实现，保留结构和署名，在数据库执行点调用 PostgreSQL 适配器，继续复用上游 service。禁止改 vendor，禁止另建平行安装器。

每个偏离上游的代码块须归入数据库、宿主兼容、已有状态过渡或已复现缺陷，并记录理由和测试。没有证据的新增机制不进入正常路径。直接继承若需要复制整段 install/uninstall 不会减少实际维护差异，因此不强求继承形式。

### 2. 按现有文件收敛

| 文件或能力 | 处理 |
| --- | --- |
| InstallLogic 的 upload/install/uninstall 和依赖流程 | 恢复对应上游结构；数据库调用定点替换 |
| PostgresLifecycleSqlExecutor | 保留候选；验证引号、注释、函数体、事务和错误传播后使用 |
| 命名空间、运行目录、前端目录、控制器入口 | 最小兼容现有 SandAdmin 标识；不得为更名迁移数据库 |
| FailedUpgrade* 七个类、Recover 命令、恢复路由 | 退出正常安装链；旧实例兼容窗口内隔离保留，不继续增强；调用方核清后再移除 |
| TerminalRunner 和异步依赖回调 | 对照上游回调完成时机；只保留当前宿主确需的连接代码，不另立依赖状态协议 |
| ZIP 路径、鉴权、覆盖边界 | 验证上游和当前实现，保留有复现依据的最小安全补丁 |
| 自动依赖插件安装和前端 activate 契约 | 不作为 PostgreSQL 适配前提；记录现有消费者及能力变化，版本切换前解决兼容说明 |

不一次性覆盖整个目录：先生成逐文件差异清单，再按调用链收敛，避免丢失未提交工作。

### 3. 数据库适配只处理 SQL 执行语义

使用宿主已配置的 PostgreSQL 连接；不建库、不读取插件私有配置替代宿主连接。支持已有 PostgreSQL 生命周期 SQL，不进行 MySQL 到 PostgreSQL 的自动翻译。安装、升级、卸载脚本统一走适配器；错误必须保留阶段和数据库诊断，不可标记成功。

优先复用现有执行器，验证显式事务指令和执行器事务的相容性。不新增迁移账本或通用元数据验证语言。跨文件/数据库原子性不作为本次承诺。

### 4. 旧状态采用兼容入口，不自动“修复”

新安装使用上游流程。已安装实例只有在版本、文件和正常状态一致时才能进入适配后的升级入口。状态 6/7/8、遗留候选或中断日志进入只读诊断并停止变更；不得强制改成 installed 或自动 retry。旧恢复实现仅服务明确的旧状态处置，不能成为新包要求。

历史恢复 API 的移除需经过调用方清点和版本化通知。无法判定的旧状态保留在原锁定宿主，不能通过部署新代码隐式迁移。该过渡不会授权当前任务操作消费宿主。

### 5. 一次通用验证后再接业务包

同一中立插件制作 v1/v2，包含 PostgreSQL 表、菜单及一个页面。实际验证零插件登录、上传安装、加载页面、升级且保留数据、卸载及宿主仍可登录。另测 SQL 失败和旧失败状态拒绝执行。前端验证采用明确的现有依赖安装/构建步骤；若需要手动构建必须写明，不能把源码复制称为激活。

只有中立链通过后才验证 SandIAM 的打包兼容；若仅业务包失败，先给出违反的具体包契约。不得同时修改宿主与插件来掩盖归属。

## Risks / Trade-offs

- 上游仍可能有非数据库缺陷 → 以最小复现证明，局部补丁并记录上游差异，不假设零缺陷。
- 回归上游可能丢失自定义能力 → 旧入口先隔离保留，明确消费者和版本切换条件。
- 旧状态误执行会重复 SQL → 进入生命周期前拒绝不兼容状态，无隐式迁移。
- 上游更新造成漂移 → 固定本次 revision；依赖更新时重新核对适配差异。
- 文档现有恢复、依赖安装及前端激活承诺与本方案冲突 → 实施时同批更新公共契约；本方案是待实施的变更，不代表现行承诺已取消。

## Migration Plan

1. 保存当前 revision 与未提交补丁清单，确认同文件没有并行写者；不重置现有分支。
2. 在源仓库实施、完成针对性回归及差异审查。实际删除旧文件前确认本轮删除授权。
3. 在获授权的独立消费验证宿主测试；建库、SQL 执行、服务启停单独落实授权，不通过测试隐式进行。
4. 发布候选前固定代码和证据，消费方主动拉取；检查实例状态后选择正常切换或保留原版本处理旧状态。
5. 若 SQL 已执行，代码回退不代表数据库回退；只使用经验证的数据库备份恢复方案。未执行 SQL 的候选可回退代码版本。不得为本次回退再建设恢复框架。
