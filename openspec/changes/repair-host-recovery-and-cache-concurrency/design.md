## Context

实际源码基线为 `07d83d591b85deb83875473687a0d033a418c778`。新安装流程在执行 SQL 前只写 `operation_pending`，失败后统一写 state 8；恢复 CLI 仅调用旧恢复逻辑。ThinkCache 文件驱动的写入锁与无锁读取不配对，标签追加也缺少完整读改写锁。

## Goals / Non-Goals

**Goals:** 为当前两份 HOST 请求提供最小宿主修复，复用安装锁、SQL 解析器、上游部署和现有缓存接口。

**Non-Goals:** 不引入业务插件专属状态，不恢复旧升级框架，不改 vendor，不添加数据库服务管理，不改消费工作区、不自动发布或部署。

## Decisions

1. 新装恢复独立于 legacy 恢复。SQL 执行器报告提交边界，新装协调代码持久化阶段；COMMIT 发出后的异常不能因 ROLLBACK 返回成功改判未提交。
2. 旧失败现场缺乏历史基线，检查统一保守归类 unknown。明确人工决策采用绑定现场的受限清理计划；不自动运行卸载脚本或推断所有同前缀对象都可删除。恢复失败和结果未知保留证据。
3. 文件缓存由宿主子类适配，锁覆盖文件操作及标签复合操作。使用不会被 cache clear 删除的稳定锁文件；损坏标签时失效缓存避免遗漏旧权限条目。保留上游序列化格式。
4. 测试分层记录：故障注入验证状态机，真实多进程文件缓存验证竞态，真实 PostgreSQL/HTTP 验收只在明确授权的隔离运行环境执行。

## Risks / Trade-offs

- [旧安装没有提交证据] → 不提供自动重试；清理需要现场与归属审核及精确确认。
- [清理事务的提交确认也可能丢失] → 持久化 unknown，不清除登记或误报成功。
- [文件数据库跨资源不原子] → 每阶段绑定现场并保留审计，重试先验证后置状态。
- [缓存锁增加争用] → 缩小到缓存操作，不在锁内执行业务控制器；压力回归记录耗时。
- [测试与正式消费宿主不同] → 实跑结果与未执行条件分别写明，不以单元测试冒充生命周期或 HTTP 验收。

## Migration Plan

由消费者主动拉取最终 clean revision；新装恢复 CLI 先 inspect，核对输出后使用它给出的精确确认。只拉取源码不自动清理现场、不重载服务。回退保留候选与恢复审计，出现新恢复记录时不得用旧版本盲目重试。
